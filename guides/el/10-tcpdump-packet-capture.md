# tcpdump: Πρακτική Συλλογή και Ανάλυση Πακέτων σε Εξουσιοδοτημένο Εργαστήριο

> **Μόνο για εξουσιοδοτημένη χρήση.** Η συλλογή πακέτων μπορεί να αποκαλύψει κωδικούς, session tokens, προσωπικά δεδομένα, εσωτερικές διευθύνσεις και περιεχόμενο εφαρμογών. Καταγράφετε μόνο σε δίκτυα και συστήματα που σας ανήκουν ή για τα οποία έχετε ρητή άδεια παρακολούθησης. Προτιμήστε lab interface, περιορίστε scope και retention, και προστατεύστε τα capture files ως ευαίσθητα στοιχεία.

## Πώς να διαβάζετε αυτόν τον οδηγό

> **Έννοια.** Μια απομαγνητοφώνηση είναι χρήσιμη μόνο αν οι συμβάσεις της είναι ρητές, γι' αυτό ο οδηγός ορίζει τρεις από την αρχή: το πλαίσιο εντολής δείχνει ακριβώς τι πληκτρολογείτε, το πλαίσιο εξόδου δείχνει τι απάντησε το μηχάνημα, και η ενδεικτική έξοδος δηλώνεται ως τέτοια. Η ίδια πειθαρχία διέπει τα φίλτρα και τις παραμέτρους παντού — καθένα εισάγεται με τον λόγο που υπάρχει, όχι μόνο με τη σύνταξή του. Ό,τι είναι μακρύτερο από λίγες προτάσεις συμπτύσσεται σε dropdown ώστε η κύρια διαδρομή να μένει ευανάγνωστη.

Κάθε βήμα εμφανίζεται με τον ίδιο τρόπο: η **εντολή** που πληκτρολογείτε, η **έξοδος** που παράγει και, στη συνέχεια, μια σύντομη επεξήγηση για το τι συνέβη και πώς να διαβάσετε το αποτέλεσμα. Για παράδειγμα:

```bash
id
```

**Έξοδος:**

```text
uid=1000(student) gid=1000(student) groups=1000(student),27(sudo)
```

Το πλαίσιο εντολής δείχνει τι ακριβώς εκτελείτε· το πλαίσιο εξόδου δείχνει τι απάντησε το μηχάνημα. Η έξοδος είναι ενδεικτική — διευθύνσεις, εκδόσεις και process IDs διαφέρουν στο δικό σας lab.

Η παράγραφος μετά από κάθε έξοδο εξηγεί *τι κάνει το εργαλείο* και *γιατί έχει σημασία το βήμα*, ώστε να μάθετε τη μέθοδο και όχι μόνο τη σύνταξη. Οτιδήποτε μεγαλύτερο — επιπλέον παράμετροι, παγίδες, θεωρία — βρίσκεται σε συμπτυσσόμενο πλαίσιο.

<details>
<summary><strong>Περισσότερα</strong> — οι συμβάσεις που ισχύουν σε όλο τον οδηγό</summary>

* **Το πλαίσιο εντολής είναι αυτό που πληκτρολογείτε· το πλαίσιο εξόδου είναι αυτό που εκτυπώνει το μηχάνημα.** Μια εντολή που πετυχαίνει συχνά δεν εκτυπώνει τίποτα — στο Linux, η σιωπή συνήθως σημαίνει επιτυχία.
* **Ένα πλαίσιο εντολής μπορεί να περιέχει πολλές γραμμές.** Όταν πολλές εντολές ανήκουν στην ίδια ιδέα ομαδοποιούνται· εκτελέστε τις με τη σειρά, μία κάθε φορά, και διαβάστε την έξοδο μετά από καθεμία.
* **Το `sudo` εκτελεί την εντολή ως διαχειριστής.** Η συλλογή απαιτεί συνήθως δικαίωμα ανοίγματος raw socket δικτύου, γι' αυτό οι περισσότερες εντολές το έχουν μπροστά.
* **Κείμενο μέσα σε γωνιώδεις αγκύλες, όπως `-i <interface>`, είναι δεσμευτικό θέσης** που αντικαθιστάτε με πραγματική τιμή. Τις ίδιες τις αγκύλες δεν τις πληκτρολογείτε ποτέ.
* **Η έξοδος είναι ενδεικτική, όχι πανομοιότυπη.** Διεπαφές, διευθύνσεις, εκδόσεις και πλήθη πακέτων διαφέρουν στο δικό σας lab. Μετράει η δομή της εξόδου, όχι τα ακριβή ψηφία.

</details>

## Τι κάνει το tcpdump

> **Έννοια.** Το `tcpdump` είναι front end χρήστη πάνω στη **libpcap**, τη φορητή βιβλιοθήκη συλλογής πακέτων, οπότε το τι μπορεί να δει κρίνεται στο link layer πριν εκτελεστεί οποιαδήποτε λογική πρωτοκόλλου. Οι επιλογείς του γράφονται στη **γλώσσα φίλτρων BPF** που τεκμηριώνεται στο `pcap-filter(7)`, μεταγλωττίζονται από τη libpcap και εκτελούνται φθηνά στον πυρήνα ή στη βιβλιοθήκη συλλογής. Το αποτέλεσμα είναι μια ροή frames του link layer, αποκωδικοποιημένων σε αναγνώσιμη σύνοψη — timestamp, endpoints, πρωτόκολλο και, για το TCP, τα control bits που περιγράφουν την κατάσταση της σύνδεσης. Επειδή τα ίδια bytes μπορεί να φαίνονται διαφορετικά σε δύο hosts, η έντιμη ανάγνωση του εργαλείου σημαίνει να διαβάζετε τη γραμμή εκκίνησης πριν από τα πακέτα.

Το `tcpdump` καταγράφει και αποκωδικοποιεί πακέτα που παρατηρεί ένα network interface. Χρησιμοποιεί το libpcap capture framework και δέχεται ισχυρή γλώσσα filters, γνωστή ως BPF syntax, ώστε να περιορίζεται η συλλογή.

Είναι χρήσιμο για troubleshooting DNS, TCP handshakes, service reachability, routing και protocol behavior. Δεν είναι intrusion tool· η κύρια αξία του είναι η προσεκτική παρατήρηση και ερμηνεία.

Ένα τυπικό packet summary περιέχει timestamp, source endpoint, destination endpoint, protocol πληροφορίες, TCP flags όπου υπάρχουν και packet length.

<details>
<summary><strong>Περισσότερα</strong> — γιατί η ίδια εντολή μπορεί να φαίνεται διαφορετική σε δύο μηχανήματα</summary>

Η ακριβής εμφάνιση διαφέρει ανά λειτουργικό, tcpdump version, link type, privileges και traffic της στιγμής. Γι' αυτό δύο hosts μπορεί να εκτυπώσουν ελαφρώς διαφορετική διάταξη για το ίδιο πακέτο, και γι' αυτό αξίζει να διαβάζετε τη γραμμή εκκίνησης κάθε capture πριν εμπιστευτείτε τις στήλες από κάτω.

</details>

## Ασφαλής εργαστηριακή αρχιτεκτονική

> **Έννοια.** Το σχήμα είναι σκίτσο ορίων εμπιστοσύνης: ο client παράγει traffic, ο capture host το παρατηρεί και το analysis workstation βλέπει μόνο ένα αντιγραμμένο αρχείο. Ο διαχωρισμός των τριών ρόλων είναι αυτός που μετατρέπει μια συλλογή σε τεκμήριο — το πρωτότυπο μπορεί να σφραγιστεί, να γίνει hash και να ξαναδιαβαστεί, ενώ ένα αντίγραφο εργασίας εξετάζεται, και τα ευαίσθητα payloads δεν χρειάζεται να ζουν σε κοινόχρηστο ή προσωπικό μηχάνημα. Τα capture files περιέχουν καταγραφή byte-προς-byte κίνησης που μπορεί να περιλαμβάνει credentials και προσωπικά δεδομένα, οπότε η αρχιτεκτονική αφορά τόσο την ελαχιστοποίηση δεδομένων και τη διατήρηση όσο και τη διασύνδεση.

Το σχήμα παρακάτω δείχνει το μικρότερο χρήσιμο lab: έναν client που ελέγχετε, έναν capture host και προαιρετικά ένα analysis workstation.

```text
+----------------------+        private network        +----------------------+
| Test client          | ----------------------------> | Capture host         |
| 192.168.56.30        |       authorized traffic      | 192.168.56.20        |
+----------------------+                                | interface: eth0      |
                                                        | tcpdump / pcap file  |
                                                        +----------+-----------+
                                                                   |
                                                                   | protected copy
                                                                   v
                                                        +----------------------+
                                                        | Analysis workstation |
                                                        | Wireshark optional   |
                                                        +----------------------+
```

Χρησιμοποιήστε test client που ελέγχετε για προβλέψιμο traffic, όπως DNS lookup, HTTP request σε local test server ή ping μέσα στο lab.

Αποθηκεύστε τα captures σε encrypted ή access-controlled θέση. Μην στέλνετε captures με ευαίσθητο traffic μέσω μη προστατευμένου chat, email ή public file-sharing.

<details>
<summary><strong>Περισσότερα</strong> — κρατήστε τη συλλογή μέσα στα όρια του lab</summary>

Ο client παράγει το traffic, ο capture host το παρατηρεί και το analysis workstation βλέπει μόνο ένα *αντίγραφο*. Ο διαχωρισμός των τριών ρόλων σημαίνει ότι ένα capture μπορεί να διαγραφεί από τον capture host χωρίς να χαθεί η ανάλυση, και κρατά τα captured payloads μακριά από κοινόχρηστα ή προσωπικά μηχανήματα.

</details>

## Εγκατάσταση και εντοπισμός interfaces

> **Έννοια.** Η εγκατάσταση του `tcpdump` είναι εγκατάσταση μηχανισμού συλλογής: το εκτελέσιμο είναι μόνο το front end, και η πραγματική δουλειά γίνεται από τη libpcap και τον μηχανισμό συλλογής πακέτων του πυρήνα — γι' αυτό το πακέτο εξαρτάται από βιβλιοθήκη και γι' αυτό απαιτείται raw socket ή capability. Στη συνέχεια, το `tcpdump -D` απαριθμεί τα interfaces στα οποία η βιβλιοθήκη επιτρέπει συλλογή, και υπάρχει επειδή τα ονόματα interfaces δεν είναι φορητά: το `eth0` σε μία διανομή είναι `ens33`, `enp0s3` ή `wlan0` σε άλλη. Η αντιγραφή του ακριβούς ονόματος από το `-D` αντί για υπόθεση του κλασικού είναι η διαφορά ανάμεσα σε συλλογή που τρέχει και σε φίλτρο που δεν βλέπει σιωπηλά τίποτα.

Σε Debian-based συστήματα, ανανεώστε το package index, εγκαταστήστε το tcpdump και καταγράψτε τα interfaces που μπορούν να συλλέξουν. Πρώτα ανανεώστε τη λίστα πακέτων:

```bash
sudo apt update
```

**Έξοδος:**

```text
Hit:1 http://deb.debian.org/debian stable InRelease
Reading package lists... Done
```

Η `apt update` ανανεώνει τα τοπικά package metadata ώστε οι επόμενες εγκαταστάσεις να βλέπουν τις τρέχουσες εκδόσεις. Δεν αλλάζει τίποτα άλλο και συνήθως τελειώνει με `Reading package lists... Done`.

Εγκαταστήστε το capture utility:

```bash
sudo apt install -y tcpdump
```

**Έξοδος:**

```text
Setting up tcpdump (4.x) ...
```

Η `apt install -y tcpdump` εγκαθιστά το tcpdump και τις εξαρτήσεις του, ενώ το `-y` απαντά αυτόματα στην ερώτηση επιβεβαίωσης. Όταν η εντολή επιστρέψει χωρίς σφάλμα, το εκτελέσιμο `tcpdump` είναι διαθέσιμο.

Καταγράψτε τα interfaces στα οποία επιτρέπεται συλλογή:

```bash
sudo tcpdump -D
```

**Έξοδος:**

```text
1.eth0 [Up, Running]
2.lo [Up, Running, Loopback]
3.any (Pseudo-device that captures on all interfaces)
```

Η `tcpdump -D` εμφανίζει τα interfaces που μπορεί να χρησιμοποιήσει το tcpdump. Το `eth0` είναι συνήθως Ethernet-style interface, το `lo` είναι local loopback και το `any` καταγράφει από πολλαπλά interfaces.

<details>
<summary><strong>Περισσότερα</strong> — τα ονόματα interfaces διαφέρουν από διανομή σε διανομή</summary>

Τα ονόματα μπορεί να είναι `ens33`, `enp0s3`, `wlan0` ή κάποιο άλλο ειδικό για τη διανομή. Γι' αυτό τρέχετε πρώτα `tcpdump -D` και αντιγράφετε το ακριβές όνομα, αντί να υποθέτετε ότι υπάρχει το κλασικό `eth0`.

</details>

Δείτε την εγκατεστημένη έκδοση και τη σύνοψη χρήσης. Πρώτα την έκδοση:

```bash
tcpdump --version
```

**Έξοδος:**

```text
tcpdump version 4.x
libpcap version 1.x
```

Η έξοδος έκδοσης δείχνει ποιο build tcpdump και ποιο build libpcap χρησιμοποιούνται· οι ακριβείς αριθμοί διαφέρουν ανά διανομή.

Έπειτα, εκτυπώστε τις πρώτες γραμμές της βοήθειας:

```bash
tcpdump --help | head -25
```

**Έξοδος:**

```text
Usage: tcpdump [ -AbdDefhHIJKlLnNOpqStuUvxX# ] ...
```

Η σύνοψη βοήθειας εμφανίζει τα διαθέσιμα options. Η διοχέτευση μέσω `head -25` κρατά την έξοδο σύντομη, δείχνοντας μόνο τις πρώτες 25 γραμμές.

## Περιορισμένη αρχική capture

> **Έννοια.** Μια συλλογή χωρίς όρια έχει δύο τρόπους αποτυχίας: ένα αρχείο που μεγαλώνει χωρίς όριο και μια ροή πολύ μεγάλη για να ελεγχθεί. Ο περιορισμός της εκτέλεσης — όριο πλήθους πακέτων (`-c`), snap length (`-s`) και φίλτρο — είναι επομένως η πρώτη συνήθεια της μεθόδου, όχι δεύτερη σκέψη. Είναι επίσης η στιγμή που διαβάζετε τη γραμμή εκκίνησης, η οποία δηλώνει το interface, το link type και το snapshot length που ισχύουν πραγματικά, γιατί κάθε επόμενη στήλη εξαρτάται από αυτά τα τρία γεγονότα.

Capture χωρίς όρια μπορεί να δημιουργήσει πολύ μεγάλα αρχεία ή να συλλέξει περισσότερα δεδομένα από όσα χρειάζεται. Ξεκινήστε με όριο πλήθους πακέτων:

```bash
sudo tcpdump -i eth0 -c 5
```

**Έξοδος:**

```text
tcpdump: verbose output suppressed, use -v[v]... for full protocol decode
listening on eth0, link-type EN10MB (Ethernet), snapshot length 262144 bytes
20:32:14.102431 IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
20:32:14.102580 IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], seq 987650, ack 125431, win 65160, length 0
5 packets captured
```

Η `-i eth0` επιλέγει interface και η `-c 5` σταματά μετά από πέντε πακέτα. Το πρώτο πακέτο είναι TCP SYN από client ephemeral port `49152` προς port 80. Το δεύτερο είναι SYN-ACK, δηλαδή η απάντηση του server στη διάρκεια του TCP three-way handshake.

Η τελευταία γραμμή επιβεβαιώνει πόσα πακέτα κατέγραψε το tcpdump. Το `verbose output suppressed` είναι φυσιολογικό· προτείνει `-v` για περισσότερη λεπτομέρεια.

Κάθε γραμμή σύνοψης απαντά στις ίδιες ερωτήσεις με την ίδια σειρά, οπότε αξίζει να ονομάσουμε τα πεδία μία φορά.

```text
20:32:14.102431 IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
```

| Πεδίο | Παράδειγμα | Σημασία |
| --- | --- | --- |
| Timestamp | `20:32:14.102431` | Χρόνος συλλογής, `hh:mm:ss.frac` από προεπιλογή |
| Network layer | `IP` | IPv4· το `IP6` δηλώνει IPv6 |
| Source endpoint | `192.168.56.30.49152` | Source address και port, ενωμένα με τελεία |
| Direction | `>` | Διαχωρίζει πηγή από προορισμό |
| Destination endpoint | `192.168.56.20.80` | Destination address και port |
| Flags | `[S]` | TCP control bits, σε αγκύλες |
| Sequence data | `seq 125430` | Sequence numbers που καλύπτονται (`first:last`, ή μία τιμή όταν το πακέτο είναι κενό) |
| Acknowledgement | `ack 125431` | Επόμενο sequence number που αναμένει ο peer· λείπει από σκέτο SYN |
| Window | `win 64240` | Διαφημιζόμενο receive window, σε bytes |
| Options | `options [mss 1460,sackOK,...]` | TCP options, εμφανίζονται σε υψηλότερη verbosity |
| Payload | `length 0` | Bytes payload που μεταφέρει το πακέτο |

Δεν εμφανίζονται όλα τα πεδία σε κάθε γραμμή: ένα σκέτο SYN δεν φέρει `ack`, και τα `options` εμφανίζονται μόνο όταν τα έχει το πακέτο και η verbosity είναι αρκετά υψηλή.

<details>
<summary><strong>Περισσότερα</strong> — η γραμμή εκκίνησης, και γιατί το όριο πλήθους είναι συνήθεια</summary>

Οι δύο πρώτες γραμμές δεν είναι πακέτα: είναι το banner εκκίνησης, που δηλώνει interface, link type (το `EN10MB` είναι Ethernet) και snapshot length. Ό,τι ακολουθεί είναι μία γραμμή ανά πακέτο.

Το όριο πλήθους (`-c`) είναι η απλούστερη προφύλαξη από τα δύο πραγματικά προβλήματα της συλλογής — ένα αρχείο που αυξάνεται χωρίς όριο και μια ροή που δεν μπορείτε πλέον να ελέγξετε ρεαλιστικά.

</details>

## Ονόματα, αριθμοί και σύντομη έξοδος

> **Έννοια.** Η επίλυση ονομάτων είναι παρενέργεια με κόστος: κάθε address ή service name που μεταφράζει το tcpdump είναι ένα lookup που μπορεί να κολλήσει σε απομονωμένο ή αργό resolver και μπορεί να αλλάξει το νόημα της γραμμής. Το `-n` απενεργοποιεί το hostname resolution και ένα δεύτερο `n` απενεργοποιεί τη μετατροπή service names, κρατώντας την έξοδο αριθμητική, γρήγορη και σαφή. Το `-q` κόβει μετά τη λεπτομέρεια πρωτοκόλλου, ανταλλάσσοντας διάγνωση με συντομία — χρήσιμο για high-level εικόνα και άχρηστο όταν τα flags και τα sequence fields είναι το ζητούμενο.

Από προεπιλογή το tcpdump μπορεί να επιλύει addresses ή service names. Απενεργοποιήστε το name resolution όταν χρειάζεστε γρηγορότερη και σαφή έξοδο:

```bash
sudo tcpdump -i eth0 -c 3 -nn
```

**Έξοδος:**

```text
20:33:01.100001 IP 192.168.56.30.53530 > 192.168.56.20.53: 1234+ A? example.test. (30)
```

Η `-n` αποφεύγει hostname resolution και η δεύτερη `n` αποφεύγει service-name conversion. Έτσι η `53` παραμένει αριθμός θύρας αντί για `domain`.

Αυτό μειώνει delays και side effects από DNS lookups κατά την ανάλυση.

Χρησιμοποιήστε quick mode όταν αρκεί μια σύντομη σύνοψη ροής:

```bash
sudo tcpdump -i eth0 -c 3 -q -nn
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: tcp 0
IP 192.168.56.20.80 > 192.168.56.30.49152: tcp 0
```

Η `-q` εμφανίζει λιγότερες protocol λεπτομέρειες. Είναι χρήσιμη για high-level εικόνα, αλλά μπορεί να κρύψει στοιχεία που χρειάζονται για διάγνωση, όπως TCP flags και sequence-related λεπτομέρειες.

<summary><strong>Περισσότερα</strong> — γιατί ένα lab προτιμά αριθμούς αντί ονόματα</summary>

Σε lab δίκτυο ο resolver είναι συχνά αργός, μη προσβάσιμος ή σκόπιμα απομονωμένος, και ένα lookup που δεν απαντά μπορεί να κολλήσει ολόκληρη τη συλλογή. Η αριθμητική έξοδος είναι επίσης σαφής: μια διεύθυνση δεν μπορεί να συγχυστεί με hostname που απλώς της μοιάζει — κάτι που μετράει όταν συγκρίνετε capture με logs ή πίνακα firewall.

</details>

## Filters για protocol, port, host και network

> **Έννοια.** Μια έκφραση BPF είναι γραμματική, όχι κατάλογος λέξεων-κλειδιών: primitives όπως `host`, `net`, `port` και `portrange` χαρακτηρίζονται κατά κατεύθυνση (`src`, `dst`) και συνδυάζονται με `and`, `or` και `not` σε ένα boolean predicate. Η κατανόησή της ως γραμματικής είναι αυτό που σας επιτρέπει να λέτε ακριβώς αυτό που εννοείτε — και στην ίδια γραμματική ανάγονται το `tcp-syn` και οι μορφές με byte offsets. Επειδή το predicate μεταγλωττίζεται και εφαρμόζεται πριν τα πακέτα φτάσουν στο tcpdump, ένα στενό φίλτρο είναι και φθηνότερο για τον capture host, όχι μόνο τακτικότερο στην ανάγνωση. Τα εισαγωγικά μετράνε: το φίλτρο πρέπει να φτάσει ως ένα όρισμα.

Το BPF filter τοποθετείται μετά από τα options του tcpdump. Καταγράψτε δέκα ICMP πακέτα στο επιλεγμένο interface:

```bash
sudo tcpdump -i eth0 -c 10 -nn icmp
```

**Έξοδος:**

```text
20:34:10.000200 IP 192.168.56.30 > 192.168.56.20: ICMP echo request, id 4512, seq 1, length 64
20:34:10.000611 IP 192.168.56.20 > 192.168.56.30: ICMP echo reply, id 4512, seq 1, length 64
```

Η πρώτη γραμμή είναι ICMP echo request, που συχνά δημιουργεί το `ping`· η δεύτερη είναι η αντίστοιχη reply. Το identifier και το sequence number βοηθούν στο ταίριασμα request και reply.

Request χωρίς reply μπορεί να υποδηλώνει firewall rule, routing πρόβλημα, host unavailability ή packet loss· δεν αποτελεί αυτόματα κακόβουλη ενέργεια.

Καταγράψτε traffic που αφορά θύρα web:

```bash
sudo tcpdump -i eth0 -c 10 -nn 'port 80'
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], length 0
```

Το filter `port 80` ταιριάζει με πακέτα όπου source ή destination port είναι 80. Για server-side destination χρησιμοποιήστε `dst port 80`· για traffic που ξεκινά από port 80 χρησιμοποιήστε `src port 80`.

Καταγράψτε μόνο το traffic που αφορά έναν host:

```bash
sudo tcpdump -i eth0 -c 10 -nn host 192.168.56.30
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], length 0
```

Το `host` ταιριάζει με πακέτα και στις δύο κατευθύνσεις που αφορούν τη συγκεκριμένη address `192.168.56.30`. Είναι ο απλούστερος τρόπος να παρακολουθείτε ό,τι στέλνει και λαμβάνει ένας host.

Περιορίστε τη συλλογή σε ολόκληρο υποδίκτυο:

```bash
sudo tcpdump -i eth0 -c 10 -nn net 192.168.56.0/24
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], length 0
```

Το `net` ταιριάζει με traffic προς ή από το δηλωμένο network. Τα στενά filters μειώνουν την άσχετη συλλογή και βελτιώνουν την αναγνωσιμότητα.

Ένα port range είναι χρήσιμο όταν δοκιμάζετε μια ομάδα σχετικών υπηρεσιών:

```bash
sudo tcpdump -i eth0 -c 10 -nn 'portrange 8000-8100'
```

Αυτό ταιριάζει με πακέτα όπου source ή destination port είναι μεταξύ 8000 και 8100 συμπεριλαμβανομένων. Χρησιμοποιήστε το μόνο όταν το range σχετίζεται· τα ευρέα ranges αυξάνουν τον θόρυβο.

Οι δείκτες κατεύθυνσης συνδυάζονται με τους παραπάνω όρους. Καταγράψτε μόνο τη διαδρομή αιτήματος του client, από μία πηγή προς μία destination port:

```bash
sudo tcpdump -i eth0 -c 5 -nn 'src host 192.168.56.30 and dst port 80'
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [.], ack 1, length 0
```

Τα `src host` και `dst port` είναι καθένα μονοκατευθυντικό, και το `and` απαιτεί και τα δύο, οπότε το αποτέλεσμα είναι μόνο η κίνηση που στέλνει ο client προς τη θύρα web.

Η άρνηση αφαιρεί την κίνηση που ήδη κατανοείτε. Αποκλείστε το SSH διαχείρισης από πολυάσχολη συλλογή:

```bash
sudo tcpdump -i eth0 -c 5 -nn 'not port 22'
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], length 0
```

Το `not port 22` ταιριάζει με κάθε πακέτο όπου source και destination port είναι και τα δύο κάτι άλλο από 22· το `not` δεσμεύει πιο στενά από το `and`, οπότε βάλτε παρενθέσεις όταν το συνδυάζετε με άλλους όρους.

Τέλος, το `tcp-syn` είναι primitive ευκολίας που αναπτύσσεται στην έκφραση μάσκας του τμήματος των flags και είναι ο συντομότερος τρόπος να παρακολουθείτε απόπειρες σύνδεσης.

```bash
sudo tcpdump -i eth0 -c 3 -nn 'tcp-syn'
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
```

Διαβάστε το `pcap-filter(7)` για την πλήρη γραμματική· τα primitives που φαίνονται εδώ — `host`, `net`, `port`, `portrange`, `src`, `dst`, `not`, `and`, `or` και οι συντομεύσεις flags — καλύπτουν την περισσότερη καθημερινή δουλειά.

<details>
<summary><strong>Περισσότερα</strong> — φτιάχνοντας ένα filter που λέει ακριβώς αυτό που εννοείτε</summary>

Η γλώσσα filters είναι γραμματική και όχι κατάλογος λέξεων-κλειδιών: συνδυάζει όρους όπως `host`, `net`, `port`, `src`, `dst` και `portrange` σε μία συνθήκη. Επειδή το filter εφαρμόζεται πριν φτάσουν τα πακέτα στο tcpdump, ένα στενό filter μειώνει και τη δουλειά του capture host.

Τα εισαγωγικά μετράνε: το `'port 80'` περνά στον compiler του filter ως ένα όρισμα, ενώ ένα άκλειδο `port 80` θα διαβαζόταν από το κέλυφος ως η λέξη `port` και μετά ως ξεχωριστό όρισμα το `80`.

</details>

## Κατεύθυνση και link-layer πληροφορίες

> **Έννοια.** Το tcpdump μπορεί να επιλέγει πακέτα κατά την κατεύθυνση στην οποία τα είδε το interface (`-Q in`/`out`) και μπορεί να εκτυπώνει το link-layer header (`-e`), αλλά και οι δύο δυνατότητες εξαρτώνται από platform και driver. Η κατεύθυνση είναι χρήσιμη όταν ξέρετε ήδη ποια πλευρά της συνομιλίας σας ενδιαφέρει — συνήθως οι απαντήσεις ενός server — και το `-e` εκθέτει τις Ethernet addresses και το ethertype που δηλώνουν από πού προήλθε φυσικά ένα frame. Οι MAC addresses έχουν νόημα μόνο στο τοπικό Layer-2 segment, γιατί κάθε router τις ξαναγράφει, οπότε μια MAC σε ένα capture περιγράφει το κοντινότερο switch ή gateway και όχι τον αρχικό αποστολέα.

Σε συστήματα που υποστηρίζουν capture direction, περιορίστε την έξοδο σε εισερχόμενα ή εξερχόμενα πακέτα. Δείξτε μόνο τα πακέτα που λαμβάνει το interface:

```bash
sudo tcpdump -i eth0 -c 5 -nn -Q in
```

**Έξοδος:**

```text
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], seq 987650, ack 125431, win 65160, length 0
```

Η `-Q in` εμφανίζει πακέτα που λαμβάνει το interface, δηλαδή εισερχόμενη κίνηση.

Δείξτε μόνο τα πακέτα που στέλνει το interface:

```bash
sudo tcpdump -i eth0 -c 5 -nn -Q out
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
```

Η `-Q out` εμφανίζει πακέτα που στέλνει το interface. Η υποστήριξη και των δύο κατευθύνσεων εξαρτάται από platform και driver· αν δεν υποστηρίζεται, το tcpdump επιστρέφει σφάλμα.

Συμπεριλάβετε headers επιπέδου Ethernet:

```bash
sudo tcpdump -i eth0 -c 2 -nn -e
```

**Έξοδος:**

```text
20:35:44.200001 08:00:27:aa:bb:01 > 08:00:27:aa:bb:20, ethertype IPv4 (0x0800), length 74: 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
```

Η `-e` εκτυπώνει link-layer πληροφορίες, όπως source και destination MAC addresses σε Ethernet captures. Το `ethertype IPv4 (0x0800)` αναγνωρίζει το network-layer protocol που μεταφέρει το frame.

<details>
<summary><strong>Περισσότερα</strong> — πότε αξίζουν η κατεύθυνση και οι MAC addresses</summary>

Αν το tcpdump αναφέρει ότι η direction δεν υποστηρίζεται, χρησιμοποιήστε host, address ή port filter. Η directional capture είναι πιο χρήσιμη όταν ξέρετε ήδη ποια πλευρά της συνομιλίας θέλετε να δείτε, για παράδειγμα τις απαντήσεις ενός server.

Οι MAC addresses έχουν συνήθως σημασία μόνο στο τοπικό Layer-2 segment: αλλάζουν σε κάθε router, οπότε μια MAC σε ένα capture σας λέει για το κοντινότερο switch ή gateway, όχι για τον αρχικό αποστολέα.

</details>

## Verbosity και timestamps

> **Έννοια.** Κάθε `v` αυξάνει το βάθος αποκωδικοποίησης και όχι τα δεδομένα που συλλέγονται: το `-v` προσθέτει τα πεδία της IPv4 κεφαλίδας όπως ορίζονται στο RFC 791, το `-vv` προσθέτει περαιτέρω ελέγχους πρωτοκόλλου όπως το TCP checksum, και το `-vvv` αποκωδικοποιεί πλήρως options και ανώτερα πρωτόκολλα. Τα timestamp switches είναι ορθογώνια — αλλάζουν την παρουσίαση και όχι το περιεχόμενο, από σκέτη ώρα (`-t`) σε απόλυτο epoch (`-tt`), διαφορά μεταξύ πακέτων (`-ttt`) και human-readable ημερομηνία (`-tttt`). Ξεκινήστε από το χαμηλότερο επίπεδο που απαντά στην ερώτησή σας, γιατί κάθε επιπλέον πεδίο είναι μια ακόμη στήλη που μπορεί να παρερμηνευθεί.

Αυξήστε το protocol detail μόνο όταν είναι χρήσιμο, ξεκινώντας με `-v`:

```bash
sudo tcpdump -i eth0 -c 2 -nn -v
```

**Έξοδος:**

```text
IP (tos 0x0, ttl 64, id 22301, offset 0, flags [DF], proto TCP (6), length 60)
    192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
```

Η `-v` προσθέτει γραμμή IPv4 header με type of service, time-to-live, packet ID, fragmentation πληροφορίες, protocol number και συνολικό μήκος.

Προσθέστε περισσότερες protocol λεπτομέρειες με δεύτερο `v`:

```bash
sudo tcpdump -i eth0 -c 2 -nn -vv
```

**Έξοδος:**

```text
IP (tos 0x0, ttl 64, id 22301, offset 0, flags [DF], proto TCP (6), length 60)
    192.168.56.30.49152 > 192.168.56.20.80: Flags [S], cksum 0xabcd (correct), seq 125430, win 64240, length 0
```

Η `-vv` προσθέτει ακόμη περισσότερα protocol fields, όπως την κατάσταση checksum του TCP τμήματος.

Κρατήστε το τρίτο επίπεδο για πραγματικά βαθύ protocol debugging:

```bash
sudo tcpdump -i eth0 -c 2 -nn -vvv
```

**Έξοδος:**

```text
IP (tos 0x0, ttl 64, id 22301, offset 0, flags [DF], proto TCP (6), length 60)
    192.168.56.30.49152 > 192.168.56.20.80: Flags [S], cksum 0xabcd (correct), seq 125430:125430, win 64240, options [mss 1460,sackOK,TS val 100 ecr 0,nop,wscale 7], length 0
```

Η `-vvv` αποκωδικοποιεί τα περισσότερα πεδία, μαζί με τα διαπραγματευμένα TCP options όπως `mss`, `sackOK`, `wscale` και timestamps. Η επιπλέον verbosity κάνει το troubleshooting ευκολότερο αλλά αυξάνει τον όγκο εξόδου.

Οι μορφές timestamps αλλάζουν την παρουσίαση, όχι το περιεχόμενο των πακέτων. Αποκρύψτε τα timestamps εντελώς με `-t`:

```bash
sudo tcpdump -i eth0 -c 2 -nn -t
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], length 0
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], length 0
```

Η `-t` αποκρύπτει τη στήλη timestamp, αφήνοντας μόνο τη σύνοψη του πακέτου.

Εμφανίστε απόλυτο Unix-style timestamp με `-tt`:

```bash
sudo tcpdump -i eth0 -c 2 -nn -tt
```

**Έξοδος:**

1759951801.102580 IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], length 0
```

Η `-tt` εμφανίζει απόλυτο Unix-style timestamp, σε δευτερόλεπτα από την εποχή (epoch).

Μετρήστε την καθυστέρηση μεταξύ πακέτων με `-ttt`:

sudo tcpdump -i eth0 -c 2 -nn -ttt
```

**Έξοδος:**

Η `-ttt` εμφανίζει τη διαφορά χρόνου από το προηγούμενο πακέτο, χρήσιμη για latency και timing analysis.

Χρησιμοποιήστε human-readable ημερομηνία με `-tttt`:

sudo tcpdump -i eth0 -c 2 -nn -tttt

Κάθε `v` προσθέτει ένα επίπεδο: η `-v` προσθέτει IP και TCP λεπτομέρειες, η `-vv` περισσότερα protocol fields, και η `-vvv` προορίζεται για πραγματικά βαθύ protocol debugging. ## Payload rendering και snapshot length

> **Έννοια.** Το snapshot length (`-s`, snaplen) είναι πόσα bytes από κάθε πακέτο αντιγράφει η libpcap· ό,τι βρίσκεται πάνω από αυτό το όριο απορρίπτεται και η περικοπή σημειώνεται στην έξοδο ως `[|proto]`. Τα payload switches (`-A`, `-x`, `-X`, `-xx`, `-XX`) καθορίζουν πώς αποδίδονται αυτά τα συλλεγμένα bytes και είναι οι πιο ευαίσθητες παράμετροι του εργαλείου, γιατί εκθέτουν περιεχόμενο εφαρμογών. Η συλλογή περισσότερων από όσα χρειάζεστε είναι επομένως απόφαση τόσο αποθήκευσης όσο και προστασίας δεδομένων.

Η εμφάνιση payload μπορεί να αποκαλύψει plaintext application content και απαιτεί ιδιαίτερη προσοχή. Σε lab, ελέγξτε περιορισμένο αριθμό πακέτων σε ASCII:

```bash
sudo tcpdump -i eth0 -c 2 -nn -A 'tcp port 8080'
```

**Έξοδος:**

```text
GET /health HTTP/1.1
Host: 192.168.56.20:8080
User-Agent: lab-client/1.0
```

Η `-A` εκτυπώνει payload ως ASCII όπου είναι δυνατό. Τα δεδομένα που φαίνονται είναι HTTP request: το `GET` ζητά τη διαδρομή `/health`, το `Host` δηλώνει τον virtual host και το port, και το `User-Agent` δείχνει το client software string.

Μην χρησιμοποιείτε αυτή την τεχνική για συλλογή passwords, cookies, authorization headers ή user content.

Δείτε τα bytes των πακέτων σε hexadecimal και ASCII:

```bash
sudo tcpdump -i eth0 -c 1 -nn -X 'tcp port 8080'
```

**Έξοδος:**

```text
0x0000:  4500 0054 1a2b 4000 4006 ...
0x0030:  4745 5420 2f68 6561 6c74 6820 4854 5450  GET /health HTTP
```

Η `-X` εκτυπώνει hexadecimal παράσταση μαζί με ASCII decoding. Οι τιμές στα αριστερά είναι byte offsets.

Το TLS είναι κρυπτογραφημένο, αλλά το handshake του δεν είναι εντελώς αδιαφανές: το Server Name Indication (SNI) στο ClientHello αποστέλλεται σε καθαρό κείμενο, οπότε μπορεί να ανακτηθεί από ASCII dump του πρώτου πακέτου του client.

```bash
sudo tcpdump -i eth0 -c 1 -nn -A 'tcp port 443'
```

**Έξοδος:**

```text
E..<..@.@.............n.(...........P..V......
.....example.test.............................
```

Η αναγνώσιμη συμβολοσειρά `example.test` είναι το SNI που ζήτησε ο client. Το Encrypted Client Hello (ECH) σχεδιάστηκε ακριβώς για να αφαιρέσει αυτό το σήμα, γι' αυτό το SNI είναι χρήσιμος αλλά φθίνων δείκτης.

Το HTTP/3 είναι επίσης κρυπτογραφημένο και δεν χρησιμοποιεί καθόλου TCP: τρέχει πάνω από QUIC στη UDP θύρα 443, οπότε ένα TCP filter το χάνει εντελώς.

```bash
sudo tcpdump -i eth0 -c 3 -nn 'udp port 443'
```

**Έξοδος:**

```text
IP 192.168.56.30.51000 > 192.168.56.20.443: UDP, length 1252
IP 192.168.56.20.443 > 192.168.56.30.51000: UDP, length 132
```

Η ροή είναι ορατή ακόμη και αν το περιεχόμενό της δεν είναι· νεότερα builds του tcpdump αποκωδικοποιούν περισσότερο από το handshake του QUIC και δέχονται `-T quic` για να εξαναγκάσουν την ερμηνεία.

Το IPv6 συλλέγεται με τον ίδιο τρόπο, με δικά του primitives: το `ip6` ταιριάζει με πακέτα IPv6 και το `icmp6` με ICMPv6.

```bash
sudo tcpdump -i eth0 -c 2 -nn ip6
```

**Έξοδος:**

```text
IP6 2001:db8::30.49152 > 2001:db8::20.80: Flags [S], seq 125430, win 64240, length 0
```

Το `IP6` αντικαθιστά το `IP` στη σύνοψη, και ο συμβολισμός `address.port` μένει ίδιος. Ένας dual-stack host χρειάζεται και τα δύο φίλτρα, γιατί το `ip` δεν ταιριάζει ποτέ με IPv6.

Το snapshot length περιορίζει πόσα bytes διατηρεί το tcpdump από κάθε πακέτο. Για σκόπιμα περιορισμένη capture:

```bash
sudo tcpdump -i eth0 -c 2 -nn -s 96 'tcp port 8080'
```

**Έξοδος:**

```text
tcpdump: listening on eth0, link-type EN10MB (Ethernet), snapshot length 96 bytes
```

Η `-s 96` κρατά έως 96 bytes ανά πακέτο. Μικρότερο snapshot μειώνει τα αποθηκευμένα δεδομένα και τον όγκο της συλλογής, αλλά μπορεί να περικόψει headers ή payload που χρειάζονται για ανάλυση.

<details>
<summary><strong>Περισσότερα</strong> — η οικογένεια των payload switches, και τι κοστίζει ένα snapshot</summary>

Το ASCII δεξιά της `-X` κάνει ορατό το αναγνωρίσιμο plaintext, ενώ το hex είναι χρήσιμο για non-printable fields. Οι σχετικές παράμετροι είναι η `-x` (hex χωρίς ASCII), η `-xx` (προσθέτει link-layer header στο hex) και η `-XX` (link-layer hex μαζί με ASCII).

Το σύγχρονο tcpdump χρησιμοποιεί συνήθως πολύ μεγαλύτερο default snapshot length, οπότε ελέγχετε τη γραμμή εκκίνησης αντί να υποθέτετε σταθερή τιμή. Ένα πολύ μικρό snapshot κόβει σιωπηλά τα headers που μπορεί να χρειαστείτε αργότερα, και η περικοπή δεν είναι εμφανής με την πρώτη ματιά.

</details>

## TCP flags και διάγνωση συνδέσεων

> **Έννοια.** Το TCP, όπως ορίζεται στο RFC 9293, μεταφέρει ένα μικρό σύνολο control bits που περιγράφουν τη μηχανή καταστάσεων μιας σύνδεσης: SYN, ACK, FIN, RST, PSH, URG, ECE και CWR, τα οποία βρίσκονται στο byte των control bits της κεφαλίδας. Το tcpdump αποδίδει τον συνδυασμό τους ως σύντομο string σε αγκύλες, και η ανάγνωσή του είναι ο γρηγορότερος τρόπος να ακολουθήσετε three-way handshake ή να αναγνωρίσετε abort. Τα bits μπορούν να ελεγχθούν απευθείας σε BPF, είτε μέσω των ονομαστικών συντομεύσεων (`tcp-syn`) είτε μέσω του byte που τα περιέχει (`tcp[13]`). Τα sequence numbers, αντίθετα, εμφανίζονται σχετικά με το πρώτο πακέτο κάθε κατεύθυνσης εκτός αν δοθεί `-S` — γι' αυτό μια ροή που ξεκίνησε από τυχαία 32-bit τιμή φαίνεται να ξεκινά από το `1`.

Τα TCP flags εξηγούν την κατάσταση μιας σύνδεσης. Ένα πακέτο μπορεί να θέσει πολλά bits ταυτόχρονα, και το tcpdump αποδίδει το σύνολο ως σύντομο string σε αγκύλες: το `S` είναι SYN, το `F` είναι FIN, το `R` είναι RST, το `P` είναι PSH, το `U` είναι URG, το `E` είναι ECE, το `W` είναι CWR και μια μόνη `.` δηλώνει ACK. Ο παρακάτω πίνακας είναι το λεξιλόγιο που διαβάζει το υπόλοιπο τμήμα.

| Flags | Bits | Σημασία σε ένα capture |
| --- | --- | --- |
| `[S]` | SYN | Το αρχικό αίτημα σύνδεσης του three-way handshake |
| `[S.]` | SYN + ACK | Η απάντηση του listener· και οι δύο πλευρές μοιράζονται πλέον τα αρχικά sequence numbers |
| `[.]` | ACK | Το ACK που ολοκληρώνει το handshake, και κάθε επόμενο ACK-only segment |
| `[P.]` | PSH + ACK | Τα δεδομένα σπρώχνονται στην εφαρμογή χωρίς αναμονή πλήρους buffer |
| `[F.]` | FIN + ACK | Ομαλό κλείσιμο: αυτή η πλευρά δεν θα στείλει άλλα δεδομένα |
| `[R]` | RST | Απότομη άρνηση ή teardown, συχνά κλειστή θύρα ή firewall device |
| `[R.]` | RST + ACK | Reset που φέρει acknowledgement, σύνηθες όταν μια σύνδεση διακόπτεται στη μέση |

Διαβασμένο ως ακολουθία, το handshake είναι `[S]`, `[S.]`, `[.]`:

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [S.], seq 987650, ack 125431, win 65160, length 0
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [.], ack 1, win 64240, length 0
```

Η πρώτη γραμμή είναι το SYN του client, η δεύτερη το SYN/ACK του server και η τρίτη το ACK του client, μετά το οποίο η σύνδεση έχει εγκατασταθεί· ένα capture που τελειώνει μετά την πρώτη γραμμή δείχνει απόπειρα που δεν απαντήθηκε ποτέ.

Καταγράψτε αρχικά SYN πακέτα με bit-mask filter:

```bash
sudo tcpdump -i eth0 -nn -c 5 'tcp[tcpflags] & (tcp-syn|tcp-ack) == tcp-syn'
```

**Έξοδος:**

```text
IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
```

Η έκφραση ταιριάζει με πακέτα όπου το SYN είναι set και το ACK δεν είναι, κάτι που συνήθως αναγνωρίζει αρχικές προσπάθειες σύνδεσης. Το bit-mask είναι πιο αξιόπιστο από strict equality, γιατί ένα πακέτο μπορεί να περιέχει επιπλέον flags.

Καταγράψτε πακέτα TCP reset:

```bash
sudo tcpdump -i eth0 -nn -c 5 'tcp[tcpflags] & tcp-rst != 0'
```

**Έξοδος:**

```text
IP 192.168.56.20.80 > 192.168.56.30.49152: Flags [R.], seq 1, ack 1, win 0, length 0
```

Το RST δηλώνει απότομο TCP reset. Μπορεί να προκύψει από κλειστή θύρα, application abort, firewall device ή network middlebox. Συσχετίστε το με service state και logs πριν αποφασίσετε την αιτία.

Εμφανίστε απόλυτους TCP sequence numbers όταν χρειάζεται:

```bash
sudo tcpdump -i eth0 -nn -S -c 3 tcp
```

Η `-S` εκτυπώνει απόλυτους sequence numbers αντί για relative. Είναι χρήσιμη για λεπτομερές protocol troubleshooting, αλλά συνήθως δεν απαιτείται σε routine review.

Το BPF μπορεί επίσης να απευθυνθεί απευθείας σε μεμονωμένα bytes μιας κεφαλίδας — έτσι ορίζονται και οι ονομαστικές συντομεύσεις `tcp-syn` και `tcp-ack`. Ταιριάξτε πακέτα όπου το byte των TCP flags είναι ακριβώς `0x02` — SYN και τίποτα άλλο:

```bash
sudo tcpdump -i eth0 -nn -c 5 'tcp[13] = 2'
```

**Έξοδος:**

```text
20:44:02.100001 IP 192.168.56.30.49152 > 192.168.56.20.80: Flags [S], seq 125430, win 64240, length 0
```

Το `tcp[13]` είναι το δέκατο τέταρτο byte της κεφαλίδας TCP, το byte των control bits, και το `= 2` επιλέγει το bit SYN. Η αυστηρή ισότητα είναι εύθραυστη, γιατί απορρίπτει και SYN που φέρει οποιοδήποτε άλλο flag — γι' αυτό η μορφή μάσκας `tcp[13] & 2 != 0` είναι ασφαλέστερη.

Η ίδια αριθμητική φτάνει και στην κεφαλίδα IP. Ταιριάξτε πακέτα με μικρό time-to-live, σύνηθες σύμπτωμα πειράματος routing ή traceroute:

```bash
sudo tcpdump -i eth0 -nn -c 3 -v 'ip[8] < 64'
```

**Έξοδος:**

```text
IP (tos 0x0, ttl 63, id 22301, offset 0, flags [DF], proto UDP (17), length 44)
    192.168.56.30.49152 > 192.168.56.20.53: UDP, length 16
```

Το `ip[8]` είναι το ένατο byte της κεφαλίδας IPv4, το πεδίο TTL, οπότε το `ip[8] < 64` ταιριάζει με κάθε πακέτο του οποίου το TTL έχει μειωθεί τουλάχιστον μία φορά. Τα byte offsets είναι εφεδρική λύση για φίλτρα που δεν μπορούν να εκφράσουν τα ονομαστικά primitives· προτιμήστε το `tcp-syn` ή τη μορφή μάσκας όταν αρκούν.

<details>
<summary><strong>Περισσότερα</strong> — διαβάζοντας τα flags ως καταστάσεις, όχι ως συμπεράσματα</summary>

Κάθε flag είναι ένα bit και ένα πακέτο μπορεί να φέρει πολλά μαζί: το `S` είναι SYN, το `S.` είναι SYN-ACK, μια μόνη `.` σημαίνει ACK χωρίς άλλο flag, και το `R.` είναι reset με ACK. Το διάβασμα των αγκυλών είναι ο γρηγορότερος τρόπος να ακολουθήσετε ένα handshake.

Ένα filter όπως `tcp[tcpflags] & tcp-syn != 0` ταιριάζει με κάθε πακέτο που έχει SYN set, ενώ η μορφή `(tcp-syn|tcp-ack) == tcp-syn` είναι αυστηρότερη και διαλέγει μόνο το αρχικό SYN. Κανένα δεν αποδεικνύει πρόθεση: ένα SYN flood και μια νόμιμη σύνδεση ξεκινούν με ακριβώς το ίδιο πακέτο.

</details>

## PCAP αρχεία: εγγραφή και ανάγνωση

> **Έννοια.** Ένα αρχείο PCAP είναι καταγραφή byte-προς-byte των frames που δόθηκαν στη libpcap, γραμμένη στη μορφή που περιγράφει το `pcap-savefile(5)`· το `-w` το γράφει, το `-r` το αναπαράγει, και επειδή είναι πιστή καταγραφή μπορεί να ξαναεξεταστεί αργότερα με άλλα φίλτρα. Αυτή ακριβώς η πιστότητα είναι ο λόγος που ένα capture file είναι τεκμήριο και πρέπει να αντιμετωπίζεται ως τέτοιο: το πρωτότυπο μένει ανέπαφο, καταγράφεται το hash του, και τα φιλτραρισμένα αντίγραφα παράγονται κάτω από άλλα ονόματα. Η εγγραφή χωρίς όριο (`-c`, rotation `-C`/`-G`) είναι αυτό που παράγει το αρχείο πολλών gigabyte που κανείς δεν μπορεί να ελέγξει.

Γράψτε raw packets σε PCAP για μεταγενέστερη ανάλυση. Αποφύγετε unlimited capture:

```bash
sudo tcpdump -i eth0 -c 100 -nn -w lab-web-test.pcap 'tcp port 8080'
```

**Έξοδος:**

```text
100 packets captured
```

Η `-w` γράφει binary packet records αντί για readable γραμμές, οπότε δεν εμφανίζεται έξοδος ανά πακέτο. Το PCAP που προκύπτει ανοίγει αργότερα με tcpdump ή graphical analyzer.

Ελέγξτε το αρχείο που δημιουργήθηκε:

```bash
ls -lh lab-web-test.pcap
```

**Έξοδος:**

```text
-rw-r----- 1 root root 42K Oct  8 20:40 lab-web-test.pcap
```

Η `ls -lh` δείχνει το μέγεθος σε human-readable μορφή, τον owner και τα permissions. Τα permissions και ο owner πρέπει να ελέγχονται, γιατί τα capture files μπορεί να περιέχουν ευαίσθητα payloads.

Διαβάστε το αρχείο χωρίς να χρειάζεστε live traffic:

```bash
tcpdump -nn -r lab-web-test.pcap
```

**Έξοδος:**

```text
reading from file lab-web-test.pcap, link-type EN10MB (Ethernet), snapshot length 262144
20:40:01.000010 IP 192.168.56.30.49152 > 192.168.56.20.8080: Flags [S], length 0
```

Η `-r` διαβάζει πακέτα από το αποθηκευμένο PCAP. Η κεφαλίδα δείχνει το link type και το snap length που καταγράφηκαν στο αρχείο.

Αυτή η επαναλήψιμη ροή επιτρέπει την ανταλλαγή φιλτραρισμένων, προστατευμένων στοιχείων αντί για την επανάληψη δραστηριότητας σε live δίκτυο.

<details>
<summary><strong>Περισσότερα</strong> — γιατί τα capture files είναι στοιχεία, όχι πρόχειρα αρχεία</summary>

Επειδή ένα PCAP είναι εγγραφή byte προς byte, πρέπει να αντιμετωπίζεται όπως κάθε άλλο στοιχείο: το πρωτότυπο μένει ανέπαφο, καταγράφεται hash, και κάθε φιλτραρισμένο ή παράγωγο αρχείο δημιουργείται χωριστά με όνομα που το δηλώνει. Ένα αρχείο `-w` με λάθος permissions είναι διαρροή που περιμένει να καταγραφεί.

Η ανάγνωση με `-r` σημαίνει επίσης ότι το ίδιο capture μπορεί να εξεταστεί ξανά με άλλα filters πολύ μετά το συμβάν — κάτι που μια προσέγγιση μόνο live δεν μπορεί να κάνει.

</details>

## Γραφική ανάλυση πακέτων

> **Έννοια.** Ένας graphical analyzer είναι διαφορετική όψη των ίδιων bytes: επανασυνθέτει TCP streams, εφαρμόζει διαδραστικά display filters και αναπτύσσει το protocol tree ενός frame — κάτι που με το μάτι στη γραμμή εντολών είναι κουραστικό. Το αντάλλαγμα είναι ότι πρόκειται για βαρύτερο, διαδραστικό εργαλείο που δεν scriptάρεται εξίσου καθαρά με το tcpdump. Δείτε τα δύο ως συμπληρωματικά — συλλογή με tcpdump και ανάλυση του προστατευμένου αντιγράφου στο γραφικό εργαλείο — και κρατήστε το αρχικό PCAP αναλλοίωτο ώστε η ανάλυση να είναι αναπαραγώγιμη.

Ένα PCAP μπορεί να μεταφερθεί με ασφάλεια σε approved analysis workstation και να ανοιχθεί στο Wireshark. Η ακόλουθη ASCII παράσταση αντικαθιστά ένα GUI screenshot:

```text
+--------------------------------------------------------------------------------+
| Packet list                                                                    |
| No.   Time        Source            Destination       Protocol  Info          |
| 1     20:40:01    192.168.56.30     192.168.56.20     TCP       49152 -> 8080 |
| 2     20:40:01    192.168.56.20     192.168.56.30     TCP       8080 -> 49152 |
+--------------------------------------------------------------------------------+
| Packet details                                                                 |
| Ethernet II > Internet Protocol Version 4 > Transmission Control Protocol     |
+--------------------------------------------------------------------------------+
| Packet bytes                                                                   |
| 0000  08 00 27 aa bb 20 08 00 27 aa bb 01 08 00 45 00 ...                     |
+--------------------------------------------------------------------------------+
```

Το επάνω τμήμα εμφανίζει packet summaries, το μεσαίο αναπτύσσει protocol fields και το κάτω εμφανίζει raw bytes. Ένας graphical analyzer είναι ιδιαίτερα χρήσιμος για follow TCP stream, display filters και protocol trees.

Διατηρήστε το αρχικό PCAP και καταγράψτε χωριστά κάθε παράγωγο ή φιλτραρισμένο αρχείο.

<details>
<summary><strong>Περισσότερα</strong> — πότε ένα γραφικό εργαλείο κερδίζει τη γραμμή εντολών</summary>

Το tcpdump είναι γρήγορο και scriptable, αλλά η ανασύσταση μιας ολόκληρης TCP ροής με το μάτι είναι κουραστική. Ένας graphical analyzer επανασυνθέτει τη ροή, επιτρέπει διαδραστικά display filters και δείχνει το protocol tree ενός frame — τα ίδια δεδομένα που συλλέγει το tcpdump, με άλλη παρουσίαση.

Δείτε τα δύο ως συμπληρωματικά: συλλογή με tcpdump και ανάλυση του προστατευμένου αντιγράφου στο γραφικό εργαλείο.

</details>

Το `tshark`, ο command-line αδελφός του Wireshark, εφαρμόζει display filters σε αποθηκευμένο capture και είναι χρήσιμο σε script.

```bash
tshark -r lab-web-test.pcap -Y 'tcp.flags.syn == 1 && tcp.flags.ack == 0'
```

**Έξοδος:**

```text
    1 20:40:01.000010 192.168.56.30 → 192.168.56.20 TCP 74 49152 → 8080 [SYN] Seq=0 Win=64240 Len=0 MSS=1460
```

Το φίλτρο `-Y` είναι η γλώσσα του Wireshark, όχι η BPF, και εκτελείται πάνω στο ήδη συλλεγμένο πακέτο και όχι στον πυρήνα — γι' αυτό συνυπάρχουν οι δύο διάλεκτοι φίλτρων.

<details>
<summary><strong>Περισσότερα</strong> — η ευρύτερη εργαλειοθήκη συλλογής</summary>

* **Wireshark** — ο graphical analyzer· καλύτερος για επανασύνθεση ροών και διάβασμα protocol tree με το χέρι.
* **tshark** — το CLI του Wireshark· μιλά display filters και εξάγει πεδία, οπότε μπαίνει σε scripts και αναφορές.
* **Zeek** — network security monitor που μετατρέπει ροή πακέτων σε δομημένα logs (`conn.log`, `http.log`, `dns.log`) αντί για πακέτα, ιδανικό όταν σας ενδιαφέρει η συμπεριφορά και όχι τα bytes.
* **ngrep** — grep για το δίκτυο, με BPF capture filters και text pattern, βολικό για γρήγορο «δείξε μου αυτή τη συμβολοσειρά στο σύρμα».
* **Το ίδιο το tcpdump** — rotation με `-C`/`-G` και `-z gzip` μετατρέπουν μεγάλη συλλογή σε οργανωμένο σύνολο συμπιεσμένων αρχείων αντί για ένα απεριόριστο.

Είναι συμπληρωματικά, όχι ανταγωνιστικά: συλλέξτε μία φορά με στενό φίλτρο και μετά σκεφτείτε πάνω στο αποτέλεσμα με όποιο εργαλείο απαντά στην ερώτηση.

</details>

## Remote capture με safeguards

> **Έννοια.** Η απομακρυσμένη συλλογή είναι πρώτα πρόβλημα ορίων εμπιστοσύνης και μετά εργαλείου: η διοχέτευση ζωντανής ροής συλλογής μέσα από το δίκτυο δημιουργεί δεύτερο, απροστάτευτο αντίγραφο που μπορεί να υποκλαπεί ή να αναπαραχθεί, και μπορεί να μεταφέρει ακριβώς τα credentials που προσπαθούσατε να παρατηρήσετε. Το ασφαλές μοτίβο είναι συλλογή τοπικά στον εξουσιοδοτημένο host με όριο, περιορισμός των permissions του αρχείου και αντιγραφή του τελικού τεκμηρίου μέσω authenticated channel. Τα δικαιώματα είναι μέρος του ίδιου ορίου: το `-Z` εγκαταλείπει το root μόλις ανοίξει η συσκευή συλλογής, ώστε η διεργασία να τρέχει υπηρεσία δικτύου χωρίς να κρατά δικαιώματα διαχειριστή.

Για εξουσιοδοτημένο remote host, γράψτε το PCAP τοπικά αντί να στέλνετε live binary stream σε μη έμπιστο προορισμό. Κάντε bounded capture στον remote host:

```bash
sudo tcpdump -i eth0 -c 50 -nn -w /var/tmp/lab-capture.pcap 'tcp port 8080'
```

**Έξοδος:**

```text
50 packets captured
```

Αυτό κάνει bounded capture στον remote host, ώστε το αρχείο να σταματήσει να μεγαλώνει μετά τα 50 πακέτα.

Έπειτα περιορίστε την read access στον owner και στην group του αρχείου:

```bash
sudo chmod 0640 /var/tmp/lab-capture.pcap
```

**Έξοδος:**

```text
```

Η `chmod 0640` περιορίζει την πρόσβαση στον owner και στη group, και πετυχαίνει σιωπηλά: όπως αλλού στο Linux, η απουσία εξόδου σημαίνει ότι η αλλαγή έγινε δεκτή.

Μεταφέρετέ το μόνο μέσω approved authenticated channel και διαγράψτε το σύμφωνα με την evidence-retention policy σας. Αποφεύγετε εντολές που εκθέτουν passwords σε shell, logs, command history ή capture data.

<details>
<summary><strong>Περισσότερα</strong> — γιατί να μη μεταδίδετε ένα capture μέσα από το δίκτυο</summary>

Η διοχέτευση ζωντανής συλλογής μέσα από το δίκτυο κάνει τη μεταφορά δεύτερο, απροστάτευτο αντίγραφο: το binary stream μπορεί να υποκλαπεί, να καταγραφεί ή να αναπαραχθεί, και μπορεί να μεταφέρει ακριβώς τα credentials που προσπαθούσατε να παρατηρήσετε. Η τοπική συλλογή και η αντιγραφή του τελικού αρχείου υπό τον έλεγχό σας κρατά τα δεδομένα σε ένα όριο εμπιστοσύνης τη φορά.

Το `chmod 0640` είναι σκόπιμο: read/write για τον owner, read για τη group, τίποτα για τους υπόλοιπους — που ταιριάζει με το πώς πρέπει να κάθεται στον δίσκο ένα ευαίσθητο τεκμήριο μέχρι να παραληφθεί.

</details>

## Promiscuous mode

> **Έννοια.** Το promiscuous mode ζητά από το interface να παραδώσει κάθε frame που μπορεί να δει, αλλά το τι μπορεί να δει το κρίνει το δίκτυο και όχι το αίτημα: σε switched segment το interface λαμβάνει και πάλι μόνο τη δική του unicast κίνηση, τα broadcasts και τα multicasts, εκτός αν το ίδιο το switch είναι ρυθμισμένο διαφορετικά. Η θέαση της κίνησης άλλου host απαιτεί επομένως mirror ή SPAN port, network TAP ή σημείο συλλογής που βρίσκεται ήδη στη διαδρομή. Το αν η παράμετρος τηρείται εξαρτάται από λειτουργικό και driver, οπότε η διαθεσιμότητα επιβεβαιώνεται στον στόχο και δεν υποτίθεται.

Σε πολλά Ethernet interfaces το tcpdump ζητά promiscuous mode ώστε το capture library να λαμβάνει frames που παρουσιάζονται στο interface. Σε switched networks, αυτό δεν εκθέτει αυτόματα όλο το traffic άλλων hosts.

Για να μην ζητηθεί promiscuous mode:

```bash
sudo tcpdump -i eth0 --no-promiscuous-mode -c 5 -nn
```

Η εντολή καταγράφει traffic που παραδίδεται κανονικά στο host interface χωρίς να αλλάζει το interface σε promiscuous mode. Είναι συχνά κατάλληλη για τη διάγνωση του traffic του ίδιου του host.

<details>
<summary><strong>Περισσότερα</strong> — τι κάνει και τι δεν κάνει το promiscuous mode</summary>

Η switch port configuration, το VLAN membership και το hardware καθορίζουν ποια frames φτάνουν πραγματικά στο interface, οπότε το promiscuous mode μόνο του δεν μετατρέπει ένα switched δίκτυο σε hub. Για να δείτε traffic άλλων hosts χρειάζεστε συνήθως mirror port, TAP ή σημείο συλλογής που βρίσκεται ήδη στη διαδρομή.

Το αν η παράμετρος τηρείται εξαρτάται από το λειτουργικό και τον driver του interface, γι' αυτό η διαθεσιμότητα και η συμπεριφορά πρέπει να επιβεβαιώνονται στον στόχο αντί να υποθέτονται.

</details>

Η συλλογή μπορεί να αποτύχει με τρεις αναγνωρίσιμους τρόπους: έλλειψη δικαιώματος, πακέτα που χάθηκαν και θύρα που δεν βλέπει ποτέ την κίνηση.

Μια συλλογή χωρίς το απαιτούμενο δικαίωμα σταματά πριν ξεκινήσει.

```bash
tcpdump -i eth0 -c 5
```

**Έξοδος:**

```text
tcpdump: eth0: You don't have permission to capture on that device
(socket: Operation not permitted)
```

Η λύση είναι να τρέξετε την εντολή με `sudo` ή να δώσετε στο εκτελέσιμο τις capabilities `CAP_NET_RAW` και `CAP_NET_ADMIN` — όχι να χαλαρώσετε permissions αλλού.

Μια συλλογή που ολοκληρώνεται αναφέρει τη δική της λογιστική, και το `dropped by kernel` είναι ο αριθμός που προσέχετε.

```text
5 packets captured
5 packets received by filter
0 packets dropped by kernel
```

Μη μηδενικός αριθμός drops σημαίνει ότι ο buffer του πυρήνα υπερχείλισε και πακέτα χάθηκαν πριν τα δει το tcpdump· πρώτος μοχλός είναι μεγαλύτερος buffer `-B` και δεύτερος ένα στενότερο φίλτρο ή μικρότερο snap length. Ένα mirror ή SPAN port ή ένα network TAP είναι αυτό που φέρνει την κίνηση άλλου host μπροστά από το interface σας εξαρχής — το promiscuous mode μόνο του δεν μπορεί να το φτιάξει.

<details>
<summary><strong>Περισσότερα</strong> — η υπόλοιπη λίστα troubleshooting</summary>

* **Φίλτρο που δεν ταιριάζει ποτέ.** Επαληθεύστε το μεμονωμένα με `tcpdump -d '<filter>'`, που τυπώνει τον μεταγλωττισμένο κώδικα αντί να συλλέγει.
* **Ψευδή σφάλματα checksum.** Interfaces που αναθέτουν τον υπολογισμό checksum σε hardware παράγουν «κακά» checksums στο capture· το `-K` καταστέλλει τον έλεγχο.
* **Μπλοκαρισμένα pipelines.** Το `tcpdump -l` κρατά τα `tee` και `head` αποκρίσιμα όταν η έξοδος δεν είναι τερματικό.
* **Χαμένα πακέτα σε πολυάσχολο link.** Αυξήστε το `-B`, στενέψτε το BPF filter, μειώστε το `-s` ή μετακινήστε το σημείο συλλογής πιο κοντά στην πηγή.
* **Capture file που διαβάζεται ως κενό.** Επιβεβαιώστε το link type στη γραμμή εκκίνησης και ότι το ίδιο φίλτρο δεν εφαρμόζεται ξανά κατά την ανάγνωση με `-r`.

</details>

## Καλές πρακτικές capture

> **Έννοια.** Η καλή πρακτική συλλογής είναι μέθοδος, όχι σύνολο παραμέτρων: θέστε πρώτα συγκεκριμένο ερώτημα, επιλέξτε το interface που μπορεί να το απαντήσει, περιορίστε το φίλτρο στην ελάχιστη κίνηση που απαντά και βάλτε όριο στην εκτέλεση ώστε το αποτέλεσμα να παραμένει ελέγξιμο. Κάθε επιλογή είναι και απόφαση προστασίας δεδομένων, γιατί τα `-A`, `-X` και τα αποθηκευμένα captures μπορεί να εκθέσουν plaintext περιεχόμενο, credentials και προσωπικά δεδομένα. Η καταγραφή time zone, host, interface, filter, tool version και file hashes είναι αυτό που κάνει τη συλλογή υπερασπίσιμη αργότερα.

- Ξεκινήστε με συγκεκριμένο ερώτημα, όπως «Λαμβάνει ο test client DNS reply;» ή «Ολοκληρώνει το local test service TCP handshake;».
- Επιλέξτε το σωστό interface και επαληθεύστε το με `tcpdump -D` και `ip -brief address`.
- Χρησιμοποιήστε στενά BPF filters, όριο πλήθους πακέτων και κατάλληλο snap length.
- Προτιμήστε `-nn` για αποφυγή name-resolution delays και ασαφών labels.
- Αντιμετωπίστε τα `-A`, `-X` και τα PCAP ως ευαίσθητα, γιατί μπορεί να αποκαλύψουν plaintext content.
- Καταγράψτε time zone, host, interface, capture filter, tool version και file hashes στις σημειώσεις διερεύνησης.
- Συσχετίστε τα πακέτα με service logs, firewall logs, routing configuration και authorized test activity πριν εξάγετε συμπεράσματα.

<details>
<summary><strong>Περισσότερα</strong> — οι παράμετροι που αξίζει να θυμάστε</summary>

Τις περισσότερες τις έχετε συναντήσει ήδη· οι υπόλοιπες εμφανίζονται σε πραγματικά περιστατικά.

| Παράμετρος | Σημασία |
| --- | --- |
| `-nn` | Απενεργοποιεί host και service name resolution· γρηγορότερα και σαφή |
| `-A` | Εκτυπώνει payload ως ASCII (ευαίσθητο· με προσοχή) |
| `-X` | Εκτυπώνει payload ως hex μαζί με ASCII |
| `-e` | Εκτυπώνει το link-layer (Ethernet) header |
| `-tttt` | Human-readable ημερομηνία πριν την ώρα |
| `-l` | Line-buffered έξοδος· κρατά τα `tcpdump \| tee` και `tcpdump \| head` αποκρίσιμα |
| `-U` | Packet-buffered εγγραφές· κάθε πακέτο φτάνει σε αρχείο `-w` μόλις φτάνει |
| `-K` | Δεν επαληθεύει checksums· κρύβει ψευδή «bad checksum» από hardware offload |
| `-B <KiB>` | Ορίζει τον buffer συλλογής του πυρήνα, τον βασικό μοχλό κατά των drops |
| `-Z <user>` | Εγκαταλείπει τα δικαιώματα root προς τον `user` αφού ανοίξει η συσκευή |
| `-d` | Τυπώνει το μεταγλωττισμένο BPF filter και τερματίζει· δείχνει τι πραγματικά επιλέγει το φίλτρο |
| `-#` / `--number` | Αριθμεί κάθε πακέτο, ώστε μια γραμμή να μπορεί να αναφερθεί μονοσήμαντα |
| `--print` | Εκτυπώνει αποκωδικοποιημένα πακέτα ενώ τα αποθηκεύει και με `-w` |

Το `-l` είναι αυτό που κρατά ένα pipeline έντιμο: χωρίς αυτό, το tcpdump buffάρει την έξοδο όταν δεν γράφει σε τερματικό, και ένα `tee` ή `head` παρακάτω δεν βλέπει τίποτα μέχρι να γεμίσει ο buffer.

</details>

<details>
<summary><strong>Περισσότερα</strong> — ολόκληρη η λίστα ελέγχου σε μία ιδέα</summary>

Πρώτα το ερώτημα, μετά το interface, μετά το filter, πάντα τα όρια. Κάθε στοιχείο της λίστας απαντά στην ίδια ανάγκη: να μπορείτε να πείτε αργότερα *γιατί* ένα πακέτο ήταν εντός πεδίου και *τι* αποδεικνύει ή δεν αποδεικνύει.

</details>

## Βασικά μαθήματα

> **Έννοια.** Ένα capture είναι παρατήρηση, όχι ετυμηγορία: ένα SYN, ένα ICMP echo request ή μια plaintext γραμμή HTTP δηλώνουν τι πέρασε από το σύρμα, όχι γιατί ή από ποιον. Η πειθαρχία είναι να συλλέγετε την ελάχιστη κίνηση που απαντά σε καθορισμένο ερώτημα και να επιβεβαιώνετε κάθε υπόθεση σε service, firewall και routing records πριν ενεργήσετε. Η γνώση πρωτοκόλλων μετατρέπει αυτά τα bytes σε εξήγηση· η αυτοσυγκράτηση κρατά τη συλλογή αναλογική και ελέγξιμη.

Το tcpdump είναι πιο αποτελεσματικό όταν συλλέγει την ελάχιστη traffic που χρειάζεται για να απαντήσει σε ένα συγκεκριμένο troubleshooting ή security ερώτημα. Η επιλογή interface, τα BPF filters, τα όρια πακέτων και η ασφαλής διαχείριση στοιχείων μετράνε όσο και η γνώση πρωτοκόλλων.

Ένα SYN, ένα ICMP request ή μια plaintext HTTP γραμμή είναι παρατήρηση που απαιτεί επιβεβαίωση με context — όχι συμπέρασμα από μόνο του.

<details>
<summary><strong>Περισσότερα</strong> — η μία πρόταση που αξίζει να θυμάστε</summary>

Συλλέξτε τα λιγότερα δυνατά, σε σύστημα που επιτρέπεται να παρακολουθείτε, και αντιμετωπίστε κάθε πακέτο ως παρατήρηση προς εξήγηση και όχι ως ετυμηγορία προς ανακοίνωση.

</details>
