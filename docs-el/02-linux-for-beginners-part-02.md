## Εισαγωγή

Το Μέρος 1ο κάλυψε το στρώμα του Linux πάνω στο οποίο χτίζονται όλα τα άλλα: το κέλυφος, το σύστημα αρχείων, το κείμενο, τα πακέτα και τα δικαιώματα. Αυτό το μέρος κατεβαίνει ένα επίπεδο πιο βαθιά, στα πράγματα που αποφασίζουν πώς συμπεριφέρεται στ' αλήθεια ένα μηχάνημα. Βλέπουμε το **δίκτυο** — τις διεπαφές που παρουσιάζει, τις διευθύνσεις και τα αναγνωριστικά υλικού που κουβαλάει, τον server που του μοιράζει διευθύνσεις, και την υπηρεσία ονομάτων που συμβουλεύεται πριν μπορέσει να συνδεθεί οπουδήποτε. Βλέπουμε τις **διεργασίες** — πώς βλέπεις ό,τι τρέχει, πώς διαβάζεις τι καταναλώνει, πώς αποφασίζεις ποια δουλειά αξίζει την προσοχή του μηχανήματος, πώς σταματάς ό,τι πήγε στραβά, και πώς κανονίζεις δουλειές να τρέχουν αργότερα. Και βλέπουμε τις **μεταβλητές περιβάλλοντος**, το ήσυχο στρώμα ρυθμίσεων που αποφασίζει ποιο πρόγραμμα τρέχει όταν πληκτρολογείς σκέτο όνομα, ποιος resolver απαντάει, και τι ξέρει ήδη ένα φρεσκοξεκινημένο κέλυφος.

Κάθε ενότητα κρατάει το ίδιο σχήμα με το Μέρος 1ο: μια απομαγνητοφώνηση των εντολών που πληκτρολογήθηκαν και της εξόδου που παρήγαγαν, και μετά εξήγηση παράγραφο-παράγραφο για το τι συνέβη και γιατί μετράει. Όπου ένα παραδοσιακό εργαλείο έχει σύγχρονη αντικατάσταση — `ifconfig` απέναντι σε `ip`, `netstat` απέναντι σε `ss`, `top` απέναντι σε `htop` — δείχνονται και τα δύο, γιατί παλιά τεκμηρίωση, ερωτήσεις συνεντεύξεων και πραγματικά μηχανήματα τα ανακατεύουν ελεύθερα.

> **Μια προειδοποίηση πριν ξεκινήσεις.** Δύο από τα τρία θέματα εδώ μπορούν να σε κλειδώσουν έξω από το μηχάνημα όπου δουλεύεις. Το να αλλάξεις διεύθυνση μέσω SSH τερματίζει τη συνεδρία σου, και το να σκοτώσεις λάθος διεργασία ρίχνει υπηρεσία που κάποιος χρησιμοποιεί. Δούλεψε σε εικονική μηχανή, πάρε πρώτα snapshot, και κράτα ανοιχτή δεύτερη κονσόλα όσο πειραματίζεσαι με το δίκτυο.

### Πώς διαβάζουμε τα transcripts

Οι συμβάσεις είναι ίδιες με του Μέρους 1ου, και αξίζει να επαναληφθούν γιατί τα prompts σε αυτό το μέρος αλλάζουν από στιγμή σε στιγμή:

* Το `root@kali:~#` είναι κέλυφος που τρέχει ως ο παντοδύναμος λογαριασμός root, και η τελική `#` είναι προειδοποίηση που αξίζει σεβασμό. Το `student@kali:~$` είναι απλός χρήστης, και το `$` σημαδεύει τη διαφορά.

* Η έξοδος καταγράφηκε σε συστήματα της οικογένειας Debian και είναι αντιπροσωπευτική και όχι πανομοιότυπη κατά byte: διευθύνσεις, διευθύνσεις MAC, PIDs, εκδόσεις πακέτων και χρονοσφραγίδες θα διαφέρουν στο δικό σου μηχάνημα. Αυτό που μετράει είναι το σχήμα της εξόδου.

## 1. Διαχείριση δικτύων

Η δικτύωση είναι κρίσιμο θέμα για όποιον κατευθύνεται προς εργασίες ασφαλείας, γιατί μεγάλο μέρος όσων θα κληθείς τελικά να ελέγξεις ζει στο δίκτυο και όχι σε ένα μόνο μηχάνημα. Ακόμα και για καθημερινή διαχείριση, δεν πας μακριά χωρίς να ξέρεις να κοιτάς μια διεπαφή, να διαβάζεις τη διεύθυνση που κρατάει, να καταλαβαίνεις ποιος server απαντάει στις αναζητήσεις ονομάτων σου, και να αλλάζεις οποιοδήποτε από αυτά σκόπιμα. Αυτή η ενότητα περπατάει τα εργαλεία που κάνουν ακριβώς αυτό, με τη σειρά που θα άπλωνες το χέρι σε αυτά: επιθεώρησε μια διεπαφή, επιθεώρησε μια ασύρματη διεπαφή, άλλαξε μια διεύθυνση, πλαστογράφησε μια διεύθυνση υλικού, ζήτα μίσθωση από server DHCP, ανάκρινε το DNS, άλλαξε ποιον resolver χρησιμοποιείς, και παράκαμψε ένα όνομα τοπικά.

Μια σημείωση πριν ξεκινήσουμε, γιατί εξηγεί γιατί μερικές εντολές παρακάτω φαίνονται παλιομοδίτικες. Τα παραδοσιακά εργαλεία είναι τα `ifconfig`, `iwconfig`, `route` και `netstat`, και προέρχονται από πακέτο που λέγεται `net-tools` και που πολλές σύγχρονες διανομές δεν εγκαθιστούν πια από προεπιλογή. Έχουν αντικατασταθεί από την εντολή `ip` (από τη σουίτα `iproute2`) και από το `ss`. Κάθε παραδοσιακή εντολή αυτής της ενότητας συνοδεύεται λοιπόν από το σύγχρονο ισοδύναμό της, και η συνήθεια που αξίζει να χτίσεις είναι να διαβάζεις και τα δύο: η παλιά τεκμηρίωση, τα παλιότερα tutorials και οι ερωτήσεις συνεντεύξεων είναι γεμάτα `ifconfig`, ενώ κάθε τρέχουσα διανομή φέρνει το `ip`.

### 1.1 `ifconfig` — ανάλυση των διεπαφών δικτύου

Η εντολή `ifconfig` είναι το πιο βασικό εργαλείο για αλληλεπίδραση με ενεργές διεπαφές δικτύου. Τρεγμένη χωρίς ορίσματα τυπώνει κάθε διεπαφή που ο πυρήνας γνωρίζει — που σε τυπικό lab μηχάνημα σημαίνει έναν φυσικό ή εικονικό προσαρμογέα Ethernet συν τη διεπαφή loopback.

```bash
root@kali:~# ifconfig
eth0: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 192.168.1.17  netmask 255.255.255.0  broadcast 192.168.1.255
        inet6 fe80::20c:29ff:fe1b:2c3d  prefixlen 64  scopeid 0x20<link>
        ether 00:0c:29:1b:2c:3d  txqueuelen 1000  (Ethernet)
        RX packets 10422  bytes 9012443 (8.5 MiB)
        RX errors 0  dropped 0  overruns 0  frame 0
        TX packets 5120  bytes 774211 (756.0 KiB)
        TX errors 0  dropped 0 overruns 0  carrier 0  collisions 0

lo: flags=73<UP,LOOPBACK,RUNNING>  mtu 65536
        inet 127.0.0.1  netmask 255.0.0.0
        inet6 ::1  prefixlen 128  scopeid 0x10<host>
        loopback  txqueuelen 1000  (Local Loopback)
        RX packets 118  bytes 9412 (9.1 KiB)
        RX errors 0  dropped 0  overruns 0  frame 0
        TX packets 118  bytes 9412 (9.1 KiB)
        TX errors 0  dropped 0 overruns 0  carrier 0  collisions 0
```

Δείχνονται δύο διεπαφές, και το να τις διαβάζεις σωστά είναι η δεξιότητα που διδάσκει αυτή η ενότητα. Η πρώτη γραμμή κάθε μπλοκ ονομάζει τη διεπαφή και τις σημαίες της: το `UP` σημαίνει ότι η διεπαφή είναι διοικητικά ενεργοποιημένη, το `RUNNING` σημαίνει ότι ο driver αναφέρει φέρον σήμα (καλώδιο συνδεδεμένο, ή εικονικός διακόπτης συνδεδεμένος), τα `BROADCAST` και `MULTICAST` περιγράφουν την κίνηση που η διεπαφή θα δέχεται, και το `mtu 1500` είναι η μέγιστη μονάδα μετάδοσης — το μεγαλύτερο φορτίο που η ζεύξη θα κουβαλήσει σε ένα πλαίσιο. Σημασία έχει όταν διαγιγνώσκεις προβλήματα κατακερματισμού. Η διεπαφή loopback έχει `mtu` 65536 γιατί δεν είναι πραγματικό καλώδιο· τίποτα δεν χρειάζεται να χωρέσει σε πλαίσιο Ethernet όταν τα πακέτα δεν βγαίνουν ποτέ από το μηχάνημα.

Η δεύτερη γραμμή κάθε μπλοκ κουβαλάει τη διευθυνσιοδότηση. Το `inet 192.168.1.17 netmask 255.255.255.0 broadcast 192.168.1.255` είναι IPv4: η διεύθυνση, η μάσκα που ορίζει ποιο κομμάτι της διεύθυνσης είναι δίκτυο και ποιο host, και η διεύθυνση που φτάνει κάθε μηχάνημα στο τοπικό τμήμα. Από αυτούς τους δύο αριθμούς μπορείς να βγάλεις νοερά το υπόλοιπο υποδίκτυο — δεξιότητα που αξίζει εξάσκηση: μια μάσκα `/24` (255.255.255.0) με διεύθυνση 192.168.1.17 σημαίνει ότι το δίκτυο είναι το 192.168.1.0, το αξιοποιήσιμο εύρος hosts είναι .1 έως .254, και το broadcast είναι .255. Η γραμμή `inet6` είναι η αυτόματα παραγόμενη link-local διεύθυνση IPv6, αναγνωρίσιμη από το πρόθεμά της `fe80::`, που υπάρχει ακόμα και σε δίκτυα όπου κανείς δεν έχει ρυθμίσει IPv6 — ένας από τους λόγους που ένα firewall τυφλό στο IPv6 είναι πραγματικό πρόβλημα.

Η τρίτη γραμμή είναι το επίπεδο ζεύξης. Το πεδίο `ether` είναι η διεύθυνση MAC, το αναγνωριστικό υλικού καμένο στην κάρτα δικτύου (ή, σε εικονική μηχανή, αποδομένο από τον hypervisor), και το `00:0c:29` ταυτοποιεί αυτήν ως εικονικό προσαρμογέα VMware. Οι διευθύνσεις MAC συζητιούνται αναλυτικά στην ενότητα 1.4, γιατί μπορούν να αλλάξουν. Μετά από αυτό, το `txqueuelen` είναι το μήκος της ουράς εκπομπής — παράμετρος συντονισμού που σπάνια θα χρειαστεί να αγγίξεις.

Το υπόλοιπο μπλοκ είναι στατιστικά. Τα `RX` και `TX` μετρούν πακέτα και bytes που ελήφθησαν και εκπέμφθηκαν από τότε που η διεπαφή ανέβηκε· οι μετρητές `errors`, `dropped`, `overruns`, `carrier` και `collisions` καταγράφουν ό,τι πήγε στραβά, και είναι το πρώτο μέρος να κοιτάξεις όταν μια ζεύξη παραπατάει: ένας σταθερά ανερχόμενος μετρητής `errors` ή `dropped` σε φυσική διεπαφή σημαίνει συνήθως χαλασμένο καλώδιο, ελαττωματική πόρτα ή αναντιστοιχία duplex. Όλοι αυτοί οι μετρητές μηδενίζονται όταν η διεπαφή κατεβαίνει και ξανανεβαίνει.

Το σύγχρονο ισοδύναμο αυτής της εντολής είναι το `ip addr` (που συχνά γράφεται `ip a`), που δείχνει τις ίδιες πληροφορίες σε διαφορετική διάταξη:

```bash
root@kali:~# ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128 
eth0             UP             192.168.1.17/24 fe80::20c:29ff:fe1b:2c3d/64
root@kali:~# ip route
default via 192.168.1.1 dev eth0 proto dhcp metric 100 
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.17 metric 100 
```

Η παράμετρος `-br` ζητάει *σύντομη* έξοδο, μία γραμμή ανά διεπαφή — αυτό που θέλεις όταν σε νοιάζει μόνο η διεύθυνση. Η δεύτερη εντολή, `ip route`, τυπώνει τον πίνακα δρομολόγησης — το σύνολο κανόνων που αποφασίζει πού πάει ένα πακέτο — και η βασική γραμμή είναι η `default via 192.168.1.1 dev eth0`, που ονομάζει την πύλη (gateway): τον δρομολογητή όπου στέλνονται τα πακέτα όταν ο προορισμός τους δεν είναι στο τοπικό υποδίκτυο. Το να ξέρεις την πύλη δεν είναι προαιρετική γνώση, γιατί η προεπιλεγμένη διαδρομή είναι αυτό που κάνει τη διαφορά ανάμεσα σε μηχάνημα που φτάνει το διαδίκτυο και μηχάνημα που μιλάει μόνο στους γείτονές του παρότι το `ifconfig` φαίνεται απόλυτα υγιές.

### 1.2 `iwconfig` — έλεγχος ασύρματων συσκευών δικτύου

Αν το μηχάνημα έχει ασύρματο προσαρμογέα, το `iwconfig` είναι το παραδοσιακό εργαλείο για ανάγνωση των ραδιοφωνικών του ρυθμίσεων: του δικτύου με το οποίο είναι συνδεδεμένο, του σημείου πρόσβασης με το οποίο μιλάει, της συχνότητας, του ρυθμού εκπομπής και της ποιότητας σήματος.

```bash
root@kali:~# iwconfig
lo        no wireless extensions.

eth0      no wireless extensions.

wlan0     IEEE 802.11  ESSID:"LAB-AP"  
          Mode:Managed  Frequency:2.437 GHz  Access Point: 3C:37:86:1A:2B:40   
          Bit Rate=72.2 Mb/s   Tx-Power=20 dBm   
          Retry short limit:7   RTS thr:off   Fragment thr:off
          Encryption key:off
          Power Management:off
          Link Quality=58/70  Signal level=-52 dBm  
          Rx invalid nwid:0  Rx invalid crypt:0  Rx invalid frag:0
          Tx excessive retries:0  Invalid misc:0   Missed beacon:0
```

Σε μηχάνημα χωρίς ασύρματο υλικό — η συνηθισμένη περίπτωση σε εικονική μηχανή — κάθε διεπαφή αναφέρει `no wireless extensions`, και αυτή είναι η αναμενόμενη έξοδος και όχι σφάλμα: οι προσαρμογείς Ethernet δεν έχουν ραδιοφωνικές ρυθμίσεις να αναφέρουν. Σε μηχάνημα που έχει ασύρματη κάρτα, το παραπάνω μπλοκ είναι αυτό που παίρνεις, και τρία πεδία αξίζει να καταλάβεις. Το `ESSID:"LAB-AP"` είναι το όνομα του ασύρματου δικτύου στο οποίο η κάρτα έχει συνδεθεί, και το `Mode:Managed` σημαίνει ότι συμπεριφέρεται ως κανονικός πελάτης. Το πεδίο `Access Point` είναι η διεύθυνση MAC του ασύρματου δρομολογητή με τον οποίο η κάρτα είναι συνδεδεμένη — χρήσιμο για δουλειά φυσικής θέσης και για ανίχνευση απατεώνα σημείου πρόσβασης που υποδύεται το δίκτυό σου. Το `Link Quality=58/70  Signal level=-52 dBm` είναι η υγεία του ραδιοφώνου: ισχύς σήματος σε dBm όπου τιμές πιο κοντά στο μηδέν είναι καλύτερες — οπότε τα −52 dBm είναι δυνατή, άνετη σύνδεση, και οτιδήποτε χειρότερο από περίπου −75 dBm θα αρχίσει να παράγει χαμένα πακέτα.

Τα πεδία με σημασία ασφαλείας είναι το `Encryption key:off`, που σου λέει αν η ζεύξη χρησιμοποιεί WEP, WPA ή τίποτα, και οι μετρητές στο κάτω μέρος. Το `Rx invalid crypt` μετράει πλαίσια που απέτυχαν στον έλεγχο ακεραιότητας — που σε ανοιχτό δίκτυο είναι απλώς θόρυβος, αλλά σε κρυπτογραφημένο μπορεί να δείχνει παρεμβολή ή επίθεση σε εξέλιξη. Η εντολή `iw` είναι η σύγχρονη αντικατάσταση (το `iw dev wlan0 link` τυπώνει τις λεπτομέρειες σύνδεσης), και το `nmcli device wifi list` είναι το εργαλείο υψηλότερου επιπέδου αν το NetworkManager διαχειρίζεται το ραδιόφωνο.

### 1.3 Αλλαγή διεύθυνσης IP

Η διεύθυνση μιας διεπαφής μπορεί να οριστεί με το χέρι, και αυτό γίνεται με εντολή μίας γραμμής: `ifconfig`, μετά η διεπαφή προς αλλαγή, μετά η διεύθυνση που θέλεις να έχει. Εδώ δίνεται στη διεπαφή Ethernet η διεύθυνση 192.168.1.13.

```bash
root@kali:~# ifconfig eth0 192.168.1.13
root@kali:~# ifconfig eth0
eth0: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 192.168.1.13  netmask 255.255.255.0  broadcast 192.168.1.255
        ether 00:0c:29:1b:2c:3d  txqueuelen 1000  (Ethernet)
        RX packets 10430  bytes 9012611 (8.5 MiB)
        TX packets 5121  bytes 774311 (756.1 KiB)
root@kali:~# ip -br addr show eth0
eth0             UP             192.168.1.13/24 fe80::20c:29ff:fe1b:2c3d/64
```

Η διεύθυνση άλλαξε αμέσως και η δεύτερη εντολή το επιβεβαιώνει: `inet 192.168.1.13` εκεί που το προηγούμενο transcript έδειχνε 192.168.1.17. Αυτό δουλεύει γιατί ο πυρήνας δεν ζητάει άδεια από τίποτα — μια διεύθυνση είναι τοπική κατάσταση, οπότε η απόδοσή της πιάνει τη στιγμή που την πληκτρολογείς. Δεν υπάρχει διαπραγμάτευση στη χειροκίνητη περίπτωση, καμία μίσθωση DHCP, και καμία ειδοποίηση προς τον δρομολογητή — πράγμα που έχει συνέπειες που αξίζει να ειπωθούν καθαρά.

Η πρώτη συνέπεια είναι ότι η αλλαγή είναι **προσωρινή**. Τίποτα δεν γράφτηκε σε αρχείο ρυθμίσεων, οπότε μια επανεκκίνηση — ή επανεκκίνηση της υπηρεσίας δικτύωσης — επιστρέφει τη διεπαφή σε ό,τι λέει η ρύθμισή της. Αν το μηχάνημα διαχειρίζεται από NetworkManager ή systemd-networkd, αυτές οι υπηρεσίες μπορεί να αντικαταστήσουν την αλλαγή σου μέσα σε δευτερόλεπτα ή στην επόμενη επανασύνδεση. Η δεύτερη συνέπεια είναι ότι το `ifconfig eth0 <διεύθυνση>` δεν αγγίζει τον πίνακα δρομολόγησης — οπότε η προεπιλεγμένη διαδρομή μπορεί να δείχνει ακόμα έξω από τη διεπαφή με διεύθυνση προέλευσης που δεν υπάρχει πια, και η συνδεσιμότητα μπορεί να σπάσει με μπερδεμένο τρόπο: η διεπαφή φαίνεται σωστά ρυθμισμένη αλλά τίποτα δεν δρομολογείται. Το ασφαλές μοτίβο — αυτό που χρησιμοποιείται σε μηχανήματα που διαχειρίζεσαι μόνιμα — είναι να επεξεργαστείς τη ρύθμιση (αρχείο Netplan YAML στο Ubuntu, προφίλ σύνδεσης κάτω από το `/etc/NetworkManager/system-connections/`, ή το `/etc/network/interfaces` σε συστήματα Debian χωρίς NetworkManager) και μετά να ξαναφορτώσεις την υπηρεσία δικτύωσης ώστε διευθύνσεις, διαδρομές και DNS να ξαναυπολογιστούν όλα μαζί.

Αν δουλεύεις μέσω SSH όταν αλλάζεις διεύθυνση, να ξέρεις ότι σχεδόν σίγουρα κόβεις το κλαδί πάνω στο οποίο κάθεσαι: τη στιγμή που η διεύθυνση προέλευσης της σύνδεσης αλλάζει, η συνεδρία πεθαίνει. Τα στάνταρ μέτρα ασφαλείας είναι να δουλεύεις από κονσόλα, να προσθέτεις τη νέα διεύθυνση *δίπλα* στην παλιά με `ip addr add 192.168.1.13/24 dev eth0` (η σύγχρονη εντολή, που προσθέτει αντί να αντικαθιστά), ή να προγραμματίζεις επαναφορά με `at` — τεχνική που θα συναντήσουμε στην ενότητα 2.9.

### 1.4 Πλαστογράφηση (spoofing) διεύθυνσης MAC

Η διεύθυνση MAC δεν είναι μόνο αναγνωριστικό· σε πολλά δίκτυα *είναι* ο έλεγχος πρόσβασης. Σημεία ασύρματης πρόσβασης με φιλτράρισμα MAC, captive portals που θυμούνται συσκευές, servers DHCP που μοιράζουν σταθερές μισθώσεις με βάση διεύθυνση υλικού, και συστήματα ελέγχου πρόσβασης δικτύου που βάζουν σε καραντίνα άγνωστα μηχανήματα — όλα παίρνουν αποφάσεις με βάση τη διεύθυνση MAC που βλέπουν. Επειδή αυτή η τιμή διαβάζεται από τις κεφαλίδες του πλαισίου και όχι από οποιονδήποτε καταχωρητή υλικού κατά τη λήψη, μια σύγχρονη κάρτα δικτύου αφήνει το λειτουργικό να παρουσιάζει όποια τιμή του ζητήσεις. Η πλαστογράφηση είναι λοιπόν τετριμμένη, και εξουδετερώνει κάθε έναν από αυτούς τους ελέγχους.

Η αλλαγή της παίρνει τρεις εντολές, γιατί οι περισσότεροι drivers δεν δέχονται νέα διεύθυνση υλικού όσο η διεπαφή μεταφέρει κίνηση: κατεβάζεις τη διεπαφή (**down**), ορίζεις τη διεύθυνση, και την ξανανεβάζεις (**up**).

```bash
root@kali:~# ifconfig eth0 down
root@kali:~# ifconfig eth0 hw ether 00:11:22:33:44:55
root@kali:~# ifconfig eth0 up
root@kali:~# ifconfig eth0
eth0: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 192.168.1.17  netmask 255.255.255.0  broadcast 192.168.1.255
        ether 00:11:22:33:44:55  txqueuelen 1000  (Ethernet)
        RX packets 2  bytes 168 (168.0 B)
        TX packets 3  bytes 252 (252.0 B)
```

Η λέξη-κλειδί `hw ether` σημαίνει «η διεύθυνση υλικού τύπου Ethernet», και το όρισμα που ακολουθεί είναι η νέα τιμή. Η επαλήθευση δείχνει `ether 00:11:22:33:44:55` στη θέση της αρχικής διεύθυνσης VMware, και πρόσεξε τι άλλο άλλαξε: οι μετρητές `RX` και `TX` μηδενίστηκαν σχεδόν — γιατί το κατέβασμα της διεπαφής τους σβήνει και το ξανανέβασμα ξεκινάει καινούριους. Αξίζει επίσης να σημειωθεί ότι η διεπαφή επανήλθε με τη ρυθμισμένη διεύθυνση IPv4 και τις διαδρομές της, γιατί αυτά εφαρμόζονται από τον διαχειριστή δικτύου όταν η ζεύξη ανεβαίνει — μια χειροκίνητη ρύθμιση μέσα σε ζωντανό σύστημα συμπεριφέρεται διαφορετικά από μία που έγινε ενώ η διεπαφή είναι κάτω.

Μερικά πρακτικά σημεία. Το σύγχρονο ισοδύναμο είναι `ip link set dev eth0 address 00:11:22:33:44:55`, με `ip link set eth0 down` και `up` γύρω του. Δεν δέχεται κάθε driver πλαστογραφημένη διεύθυνση, και δεν γίνεται δεκτή κάθε διεύθυνση: μια διεύθυνση multicast (το λιγότερο σημαντικό bit της πρώτης οκτάδας αναμμένο), ή τιμή που η πρώτη της οκτάδα είναι περιττή σε λάθος θέση, μπορεί να απορριφθεί με `SIOCSIFHWADDR: Cannot assign requested address`. Διάλεξε διεύθυνση unicast — το δεύτερο λιγότερο σημαντικό bit της πρώτης οκτάδας πρέπει να είναι σβηστό — και, για οτιδήποτε χρειάζεται να φαίνεται νόμιμο, διεύθυνση με πραγματικό πρόθεμα κατασκευαστή.

Το να αλλάζεις τη MAC σου δεν είναι αορατότητα. Σε μεταγόμενο δίκτυο το πλαίσιο παραδίδεται με βάση τη MAC, αλλά ο διακόπτης *καταγράφει* σε ποια πόρτα εμφανίζεται κάθε διεύθυνση — οπότε η πλαστογράφηση διεύθυνσης που άλλη συσκευή ήδη χρησιμοποιεί δημιουργεί κατάσταση πόρτας που τρεμοπαίζει (flapping), που το λογισμικό διαχείρισης διακοπτών θα καταγράψει και πολλοί θα μπλοκάρουν. Χαρακτηριστικά προστασίας spanning-tree όπως port security και DHCP snooping, και κάθε σοβαρή ανάπτυξη ελέγχου πρόσβασης δικτύου, χτίστηκαν ακριβώς για να πιάνουν αυτό. Και αν ο στόχος σου είναι να *νικήσεις* έλεγχο πρόσβασης βασισμένο σε MAC σε αξιολόγηση, το έντιμο εύρημα να γράψεις δεν είναι «πλαστογράφησα μια MAC» αλλά «το δίκτυο αντιμετωπίζει ένα πλαστογραφήσιμο αναγνωριστικό ως παράγοντα πιστοποίησης — που σημαίνει καθόλου πιστοποίηση».

### 1.5 Παίρνοντας φρέσκια διεύθυνση από DHCP με `dhclient`

Η χειροκίνητη διευθυνσιοδότηση είναι χρήσιμη για lab, αλλά τα περισσότερα μηχανήματα δεν στέκονται ακίνητα: ζητούν από τον τοπικό server DHCP μια διεύθυνση κάθε φορά που συνδέονται. Το DHCP — το Πρωτόκολλο Δυναμικής Ρύθμισης Host — μοιράζει διευθύνσεις, και συνήθως μάσκα υποδικτύου, πύλη και servers DNS μαζί τους, από δεξαμενή που ο διαχειριστής ελέγχει. Σε μηχάνημα πελάτη το αίτημα γίνεται από τον DHCP client daemon, που σε πολλά συστήματα Linux είναι ο `dhclient`.

```bash
root@kali:~# dhclient eth0
root@kali:~# ifconfig eth0
eth0: flags=4163<UP,BROADCAST,RUNNING,MULTICAST>  mtu 1500
        inet 192.168.1.17  netmask 255.255.255.0  broadcast 192.168.1.255
        ether 00:11:22:33:44:55  txqueuelen 1000  (Ethernet)
        RX packets 421  bytes 38112 (37.2 KiB)
        TX packets 388  bytes 74520 (72.8 KiB)
```

Το να τρέχεις `dhclient` με όνομα διεπαφής ξεκινάει τον πελάτη πάνω σε αυτή τη διεπαφή, και η διεύθυνση επέστρεψε πια σε `192.168.1.17` — την τιμή που ο server είχε αποδώσει σε αυτή τη διεπαφή πριν πληκτρολογήσουμε το 192.168.1.13 από πάνω της. Το μηχάνημα επέστρεψε σε κατάσταση διαχειριζόμενη από server, και η χειροκίνητα ορισμένη διεύθυνση έφυγε από τη διεπαφή — παρότι η χειροκίνητη διεύθυνση μπορεί να επιζεί ακόμα στο ίδιο το αρχείο ρυθμίσεων του DHCP client μέχρι να ξαναγραφτεί.

Οι περισσότερες χρήσιμες λεπτομέρειες δεν τυπώνονται στην κονσόλα αλλά γράφονται στο αρχείο μισθώσεων, που καταγράφει ακριβώς τι πρόσφερε ο server και πότε λήγει:

```bash
root@kali:~# grep -A3 "lease" /var/lib/dhcp/dhclient.eth0.leases | head -20
lease {
  interface "eth0";
  fixed-address 192.168.1.17;
  option subnet-mask 255.255.255.0;
  option routers 192.168.1.1;
  option domain-name-servers 192.168.1.1;
  option dhcp-lease-time 3600;
  option dhcp-message-type 5;
  renew 4 2026/10/09 13:20:11;
  rebind 4 2026/10/09 13:50:11;
  expire 4 2026/10/09 14:05:11;
}
```

Αυτό το μπλοκ είναι η καταγραφή της συνομιλίας από τον πελάτη: η διεύθυνση που κρατάει, η μάσκα, η πύλη (`option routers`), οι servers DNS που του είπαν να χρησιμοποιεί, η διάρκεια της μίσθωσης σε δευτερόλεπτα, και οι χρόνοι στους οποίους θα προσπαθήσει να ανανεώσει, να ξαναδεθεί και τελικά να χάσει τη διεύθυνση. Αυτοί οι τρεις χρόνοι ορίζουν τον κύκλο ζωής DHCP και εξηγούν ένα συνηθισμένο γρίφο. Μια μίσθωση δεν είναι μόνιμη — οπότε μηχάνημα που ήταν κλειστό για καιρό μπορεί να επιστρέψει σε διαφορετική διεύθυνση· και επειδή ο πελάτης ανανεώνει στο μισό χρόνο μίσθωσης, μια διεύθυνση που «άλλαξε ξαφνικά» σημαίνει συνήθως ότι ο server την είχε ήδη δώσει σε κάποιον άλλον.

Δύο εντολές συμπληρώνουν το σετ. Το `dhclient -r eth0` *απελευθερώνει* τη μίσθωση, λέγοντας στον server ότι η διεύθυνση δεν χρειάζεται πια ώστε να επιστραφεί στη δεξαμενή — χρήσιμο όταν θέλεις να εξαναγκάσεις εντελώς φρέσκια ρύθμιση. Το `dhclient -v eth0` τρέχει τον πελάτη φλύαρα και τυπώνει τη χειραψία τεσσάρων βημάτων καθώς συμβαίνει (DISCOVER, OFFER, REQUEST, ACK) — ο καθαρότερος τρόπος να καταλάβεις το πρωτόκολλο και ο γρηγορότερος τρόπος να αποδείξεις ότι ένας server DHCP είναι προσβάσιμος. Στα σύγχρονα desktop συστήματα όλα αυτά διαχειρίζονται από NetworkManager ή systemd-networkd, και το να απλώνεις το χέρι στο `dhclient` με το χέρι σε τέτοιο μηχάνημα οδηγεί τα δύο συστήματα να παλεύουν πάνω στη διεπαφή· τα `nmcli con up <σύνδεση>` και `networkctl reconfigure <ζεύξη>` είναι οι ευγενικοί τρόποι να ζητήσεις.

### 1.6 Εξέταση του DNS με `dig`

Το DNS είναι η υπηρεσία που μεταφράζει ένα όνομα χώρου όπως το `example.com` στη διεύθυνση IP όπου ένα πακέτο μπορεί στ' αλήθεια να σταλεί — και κάνει πολύ περισσότερα: δημοσιεύει ποιοι servers δέχονται αλληλογραφία για έναν χώρο, ποιοι name servers είναι authoritative για τη ζώνη, ποιοι hosts υπάρχουν, και πού βρίσκονται υπηρεσίες όπως web και VPN endpoints. Για όποιον αξιολογεί στόχο, το DNS είναι χρυσός αναγνώρισης, και το `dig` — ο Domain Information Groper — είναι το εργαλείο που το διαβάζεις.

Τρεγμένο με ένα όρισμα, το `dig` κάνει αναζήτηση για εγγραφή A (διεύθυνση IPv4) και τυπώνει ολόκληρη την απάντηση, συμπεριλαμβανομένων των κομματιών που κανονικά κρύβονται:

```bash
root@kali:~# dig example.com

; <<>> DiG 9.18.24-1-Debian <<>> example.com
;; global options: +cmd
;; Got answer:
;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 41233
;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1

;; OPT PSEUDOSECTION:
; EDNS: version: 0, flags:; udp: 1232
;; QUESTION SECTION:
;example.com.			IN	A

;; ANSWER SECTION:
example.com.	3600	IN	A	93.184.216.34

;; Query time: 24 msec
;; SERVER: 192.168.1.1#53(192.168.1.1) (UDP)
;; WHEN: Fri Oct 09 12:34:56 UTC 2026
;; MSG SIZE  rcvd: 56
```

Διαβάζοντας από πάνω: η γραμμή `HEADER` αναφέρει τη λειτουργία (`opcode: QUERY`), τον κωδικό αποτελέσματος (`status: NOERROR`, όπου το NXDOMAIN σημαίνει ότι το όνομα δεν υπάρχει και το SERVFAIL ότι ο ίδιος ο resolver απέτυχε), και τις σημαίες — από τις οποίες οι `qr` (αυτό είναι απόκριση), `rd` (ζητήθηκε αναδρομή) και `ra` (διατίθεται αναδρομή) είναι αυτές που θα βλέπεις περισσότερο. Η `QUESTION SECTION` επαναλαμβάνει το ερώτημα που τέθηκε, και η `ANSWER SECTION` κρατάει την απάντηση: το όνομα, το TTL σε δευτερόλεπτα (3600, δηλαδή οι resolvers μπορούν να κρατήσουν αυτό στην cache για μία ώρα), την κλάση (`IN` για internet), τον τύπο εγγραφής (`A`) και τα δεδομένα (`93.184.216.34`).

Οι τέσσερις τελευταίες γραμμές είναι αυτές που οι αρχάριοι προσπερνούν και οι ειδικοί διαβάζουν πρώτες. Το `Query time: 24 msec` είναι πόσο πήρε η αναδρομική επίλυση. Το `SERVER: 192.168.1.1#53(192.168.1.1) (UDP)` ονομάζει τον resolver που απάντησε *σε σένα* στ' αλήθεια — εδώ την lab πύλη που προωθεί για λογαριασμό σου. Το να προσέχεις πότε αυτό αλλάζει είναι ο τρόπος να επιβεβαιώνεις ότι η ρύθμιση resolver σου έπιασε. Το `WHEN` είναι η χρονοσφραγίδα, και το `MSG SIZE rcvd` το μέγεθος της απόκρισης — αριθμός που γίνεται ενδιαφέρων όταν οι αποκρίσεις DNS μεγαλώνουν αρκετά για να πυροδοτήσουν fallback σε TCP ή κατακερματισμό.

Διαφορετικοί τύποι εγγραφών απαντούν διαφορετικά ερωτήματα, και το `dig` τους ζητάει προσθέτοντας τον τύπο στην εντολή. Ο τύπος `mx` δείχνει τους mail exchangers του χώρου — βήμα ένα στη χαρτογράφηση της mail υποδομής ενός οργανισμού:

```bash
root@kali:~# dig example.com mx +noall +answer
example.com.		3600	IN	MX	0 .
```

Αυτή η απάντηση είναι ένα **null MX**, και αξίζει να το καταλάβεις αντί να το προσπεράσεις. Η μοναδική εγγραφή `0 .` — προτεραιότητα μηδέν, στόχος η ρίζα — είναι σκόπιμος, ορισμένος-από-πρότυπα τρόπος να πεις «αυτός ο χώρος δεν δέχεται καθόλου αλληλογραφία». Ένας resolver που το βρίσκει πρέπει να σταματήσει να ψάχνει — γι' αυτό υπάρχει η εγγραφή: λέει στον κόσμο να μην μπει καν στον κόπο. Ένας χώρος που *δέχεται* αλληλογραφία επιστρέφει μία ή περισσότερες εγγραφές με hostname και αριθμό προτίμησης. Αφού ο δεσμευμένος χώρος που χρησιμοποιήθηκε παραπάνω σκόπιμα δεν δέχεται αλληλογραφία, ορίστε το σχήμα απάντησης που δέχεται αλληλογραφία, παρμένο από lab ζώνη στο top-level domain `.example` — που είναι δεσμευμένο ακριβώς γι' αυτόν τον σκοπό και άρα δεν μπορεί να συγκρουστεί με τίποτα πραγματικό:

```bash
root@kali:~# dig intranet.example mx +noall +answer
intranet.example.	300	IN	MX	10 mail1.intranet.example.
intranet.example.	300	IN	MX	20 mail2.intranet.example.
```

Εδώ δημοσιεύονται δύο mail servers, ο `mail1` προτιμώμενος από τον `mail2` γιατί ο μικρότερος αριθμός κερδίζει — έτσι ένας χώρος ισορροπεί εισερχόμενη αλληλογραφία και παρέχει εφεδρεία. Και τα δύο hostnames είναι χρήσιμα σε αξιολογητή: το καθένα είναι μηχάνημα που δέχεται μη έμπιστη είσοδο από το διαδίκτυο, και το καθένα πρέπει να επιλυθεί παραπέρα πριν ξέρεις με τι έχεις να κάνεις.

Ο τύπος `ns` ονομάζει τους authoritative name servers της ζώνης — τα μηχανήματα που κρατούν τα οριστικά αντίγραφα κάθε εγγραφής της:

```bash
root@kali:~# dig example.com ns +noall +answer
example.com.		172800	IN	NS	a.iana-servers.net.
example.com.		172800	IN	NS	b.iana-servers.net.
```

Για αξιολόγηση αυτοί είναι οι servers που θα ρωτούσες κατευθείαν (`dig @a.iana-servers.net example.com AXFR`) με την πιθανότητα να επιτρέπουν μεταφορά ζώνης — που θα παρέδιδε ολόκληρα τα περιεχόμενα της ζώνης DNS, κάθε hostname, κάθε mail server, κάθε υποχώρο που ο οργανισμός έχει καταχωρίσει ποτέ, σε ένα αίτημα. Οι σύγχρονοι servers το αρνούνται, αλλά αυτοί που δεν το αρνούνται παραμένουν από τα καλύτερα διαθέσιμα ευρήματα.

Μερικές συντομεύσεις κάνουν το `dig` ευχάριστο σε scripts και στη βιασύνη. Το `+short` τυπώνει μόνο τα δεδομένα απάντησης — οπότε το `dig +short example.com` επιστρέφει μία γραμμή που ταΐζεται τετριμμένα σε άλλη εντολή. Το `+noall +answer` πετάει τα μπλοκ κεφαλίδας και κατάστασης όταν θέλεις μόνο τις εγγραφές. Το `@1.1.1.1` στέλνει το ερώτημα σε συγκεκριμένο resolver αντί για τον προεπιλεγμένο του συστήματος — έτσι συγκρίνεις τι βλέπουν διαφορετικοί resolvers. Και οι δύο απαντήσεις δεν είναι πάντα ίδιες, γιατί ένας εσωτερικός resolver μπορεί να ξέρει ονόματα που το δημόσιο DNS δεν ξέρει, ενώ ένας δημόσιος μπορεί να απαντάει πρόθυμα για ονόματα που το εσωτερικό φιλτράρισμα κρύβει. Το `-x` κάνει αντίστροφη αναζήτηση, μετατρέποντας διεύθυνση σε όνομα (`dig -x 93.184.216.34`). Και το `+trace` ακολουθεί την επίλυση βήμα-βήμα από τους root servers προς τα κάτω — ο καλύτερος τρόπος να *μάθεις* πώς δουλεύει στ' αλήθεια το DNS αντί απλώς να διαβάζεις γι' αυτό.

### 1.7 Αλλαγή του DNS server σου

Ο resolver που το μηχάνημά σου χρησιμοποιεί από προεπιλογή περιγράφεται σε αρχείο απλού κειμένου, το `/etc/resolv.conf`, και αξίζει να το διαβάσεις πριν το αλλάξεις:

```bash
root@kali:~# cat /etc/resolv.conf
# Generated by NetworkManager
search lab.local
nameserver 192.168.1.1
```

Δύο οδηγίες εμφανίζονται σε τυπικό αρχείο. Η γραμμή `nameserver` ονομάζει τον resolver να ρωτήσεις — εδώ την lab πύλη, που προωθεί ερωτήματα προς τα πάνω — και η γραμμή `search` δείχνει χώρους που προσαρτώνται σε μη πλήρη ονόματα. Γι' αυτό το να πληκτρολογείς `ping fileserver` δουλεύει σε εταιρικό δίκτυο χωρίς πλήρως επιλεγμένο όνομα. Ένα αρχείο μπορεί να δείχνει μέχρι τρεις γραμμές `nameserver`, και συμβουλεύονται με σειρά: ο resolver ρωτάει τον πρώτο, και κατεβαίνει στη λίστα μόνο αν αυτός από πάνω δεν απαντήσει εγκαίρως. Αυτή η σειρά είναι ο λόγος που μια μπαγιάτικη καταχώριση στην κορυφή της λίστας προκαλεί τις μυστηριώδεις παύσεις που όλοι βιώνουν τελικά.

Το να αλλάξεις resolver είναι θέμα να γράψεις νέα γραμμή στο αρχείο. Ο γρηγορότερος τρόπος είναι με το `echo` του κελύφους και την ανακατεύθυνση `>`, που *αντικαθιστά* το αρχείο με ό,τι δίνεις:

```bash
root@kali:~# echo "nameserver 1.1.1.1" > /etc/resolv.conf
root@kali:~# cat /etc/resolv.conf
nameserver 1.1.1.1
root@kali:~# dig example.com +short @1.1.1.1
93.184.216.34
root@kali:~# dig example.com | grep "SERVER:"
;; SERVER: 1.1.1.1#53(1.1.1.1) (UDP)
```

Ο τελεστής `>` είναι καταστροφικός και δεν υπάρχει αναίρεση — γι' αυτό αξίζει να σημειωθεί ότι το `cat /etc/resolv.conf` ήρθε *πριν* την αλλαγή: με αρχείο μίας γραμμής δεν έχει σημασία, αλλά η ίδια συνήθεια εφαρμοζόμενη σε αρχείο ρυθμίσεων που δεν έχεις διαβάσει είναι ο τρόπος που οι άνθρωποι καταστρέφουν ρυθμίσεις που δεν μπορούν να ανακατασκευάσουν. Μετά τη γραφή, το αρχείο περιέχει ακριβώς μία γραμμή — τον δημόσιο resolver της Cloudflare στο 1.1.1.1, που θυμάται εύκολα και χρησιμοποιείται πλατιά· ο δημόσιος resolver της Google στο 8.8.8.8 και το Quad9 στο 9.9.9.9 είναι οι άλλοι δύο που θα συναντήσεις συχνότερα, και ο καθένας τους έχει δημοσιευμένη πολιτική απορρήτου που αξίζει να διαβάσεις πριν τον κάνεις resolver σου. Το δεύτερο `dig` επιβεβαιώνει ότι η αλλαγή έπιασε με τον τρόπο που μετράει: η γραμμή `SERVER:` αναφέρει πια `1.1.1.1#53` αντί για την τοπική πύλη — που αποδεικνύει ότι τα ερωτήματα βγαίνουν στ' αλήθεια από τον νέο resolver, κι όχι απλώς ότι άλλαξαν τα περιεχόμενα του αρχείου.

Υπάρχει μία σημαντική προειδοποίηση και πιάνει τους πάντες. Στα περισσότερα σύγχρονα συστήματα το `/etc/resolv.conf` *παράγεται*, δεν συντάσσεται: το NetworkManager, ο `dhclient`, το `systemd-resolved` ή το `resolvconf` το ξαναγράφει σε κάθε γεγονός δικτύου, και μπορεί ακόμα να αντικαθιστά το αρχείο με συμβολικό σύνδεσμο που δείχνει σε κατάλογο runtime. Ένα αρχείο επεξεργασμένο με το χέρι επιζεί λοιπόν μόνο μέχρι την επόμενη ανανέωση μίσθωσης DHCP ή επανεκκίνηση. Οι ανθεκτικές προσεγγίσεις είναι να ορίσεις τον DNS server στο εργαλείο που κατέχει το αρχείο — `nmcli con mod <όνομα> ipv4.dns 1.1.1.1` για NetworkManager, stanza `nameservers:` Netplan σε Ubuntu Server, ή `/etc/systemd/resolved.conf` και μετά `systemctl restart systemd-resolved` — ή, για μηχάνημα που ελέγχεις πλήρως, να κάνεις το αρχείο αμετάβλητο με `chattr +i /etc/resolv.conf`. Η τελευταία επιλογή δουλεύει και είναι καμιά φορά η σωστή απάντηση σε lab μηχάνημα, αλλά είναι παγίδα σε οτιδήποτε άλλο: κάθε μεταγενέστερη αλλαγή δικτύου θα αποτυγχάνει, και ο επόμενος διαχειριστής θα ξοδέψει απόγευμα αναρωτώμενος γιατί.

Για δουλειά ασφαλείας ο resolver μετράει για δύο λόγους. Πρώτον, ο DNS server βλέπει κάθε όνομα που αναζητάς — οπότε σε μη έμπιστο δίκτυο ένας απατεώνας resolver διαβάζει την αναγνώρισή σου και μπορεί να απαντάει με πλαστές διευθύνσεις. Δεύτερον, η χρήση resolver που επικυρώνει DNSSEC ή φιλτράρει κακόβουλους χώρους αλλάζει τι μπορείς να φτάσεις — γι' αυτό οι αξιολογήσεις ξεκινούν συχνά εντοπίζοντας ποιους resolvers χρησιμοποιεί ένα περιβάλλον στόχου και αν αυτά τα ερωτήματα κρυπτογραφούνται με DNS-over-HTTPS ή DNS-over-TLS.

### 1.8 Αντιστοίχιση hostnames στο `/etc/hosts`

Πριν σταλεί οποιοδήποτε ερώτημα DNS, το σύστημα συμβουλεύεται ένα τοπικό αρχείο. Το `/etc/hosts` είναι ένας στατικός πίνακας αντιστοιχίσεων ονόματος-σε-διεύθυνση, και κάθε σύστημα τύπου Unix έχει ένα· συμβουλεύεται πρώτο λόγω της σειράς αναζήτησης που ορίζεται στο `/etc/nsswitch.conf`, όπου η γραμμή `hosts:` γράφει `files dns` — δηλαδή «έλεγξε τα αρχεία πρώτα, μετά ρώτα το DNS».

```bash
root@kali:~# cat /etc/hosts
127.0.0.1	localhost
127.0.1.1	kali
::1		localhost ip6-localhost ip6-loopback

# The following lines are desirable for IPv6 capable hosts
ff02::1		ip6-allnodes
ff02::2		ip6-allrouters
root@kali:~# nano /etc/hosts
root@kali:~# cat /etc/hosts
127.0.0.1	localhost
127.0.1.1	kali
::1		localhost ip6-localhost ip6-loopback

# The following lines are desirable for IPv6 capable hosts
ff02::1		ip6-allnodes
ff02::2		ip6-allrouters
192.168.1.9	portal.example.com
```

Η μορφή του αρχείου είναι σκόπιμα πρωτόγονη: μια διεύθυνση IP στην πρώτη στήλη, ένα ή περισσότερα ονόματα μετά χωρισμένα με κενά, και `#` που ξεκινάει σχόλιο. Οι προεπιλεγμένες καταχωρίσεις αντιστοιχίζουν το `localhost` στις διευθύνσεις loopback και δίνουν στο μηχάνημα το δικό του hostname (`kali`) στο `127.0.1.1` — σύμβαση της οικογένειας Debian που κρατάει το hostname επιλύσιμο ακόμα και χωρίς καθόλου δίκτυο. Η γραμμή `::1` δείχνει ότι πολλά ονόματα μπορούν να προσαρτηθούν στην ίδια διεύθυνση — έτσι φτιάχνονται ψευδώνυμα.

Το να προσθέτεις γραμμή αντιστοιχίζει οποιοδήποτε όνομα της επιλογής σου σε οποιαδήποτε διεύθυνση, και επειδή το αρχείο κερδίζει το DNS, το αποτέλεσμα είναι άμεσο και καθολικό για το μηχάνημα:

```bash
root@kali:~# getent hosts portal.example.com
192.168.1.9     portal.example.com
root@kali:~# curl -s -o /dev/null -w "%{http_code} %{remote_ip}\n" http://portal.example.com/
200 192.168.1.9
root@kali:~# dig +short portal.example.com
93.184.216.34
```

Οι τρεις εντολές δείχνουν την παράκαμψη από τρεις γωνίες, και η τρίτη είναι η ενδιαφέρουσα. Το `getent hosts` ρωτάει τον ίδιο τον resolver του συστήματος — τον ίδιο μηχανισμό που οι εφαρμογές χρησιμοποιούν — και αναφέρει τη διεύθυνση από το αρχείο hosts. Το `curl` μετά συνδέεται στο `192.168.1.9` ενώ το URL λέει ακόμα `portal.example.com` — ακριβώς το είδος ανακατεύθυνσης για το οποίο αυτό το αρχείο χρησιμοποιείται. Αλλά το `dig` παρακάμπτει εντελώς το `/etc/hosts`, γιατί μιλάει κατευθείαν σε DNS servers, και επιστρέφει ακόμα την πραγματική, δημόσια διεύθυνση. Αυτή η ασυμφωνία είναι υπέροχο διδακτικό παράδειγμα της διαφοράς ανάμεσα στην *άποψη του συστήματος* και την *άποψη του DNS* — και είναι επίσης ο λόγος που ένα όνομα που δουλεύει στον browser μπορεί να αποτυγχάνει σε script που χρησιμοποιεί `dig` ή `nslookup`: τα δύο απαντούν διαφορετικά ερωτήματα.

Οι νόμιμες χρήσεις του αρχείου είναι παντού: να δίνεις σε lab μηχάνημα φιλικό όνομα πριν υπάρξει DNS, να δοκιμάζεις νέο web server πριν αλλάξει η εγγραφή DNS του, να καρφώνεις hostname ώστε μια εσωτερική εφαρμογή να σταματήσει να επιλύει σε λάθος διεύθυνση, και να μπλοκάρεις χώρο δείχνοντάς τον στο `127.0.0.1` ή `0.0.0.0`. Η παράνομη χρήση είναι που το κάνει σχετικό εδώ, και είναι ο ίδιος μηχανισμός ανάποδα: επειδή το αρχείο είναι τοπικό και έμπιστο, ένας επιτιθέμενος που μπορεί να γράψει σε αυτό — ή που μπορεί να τρέξει απατεώνα DHCP ή DNS server που απαντάει πρώτος — μπορεί να στέλνει χρήστη σε server της επιλογής του. Αυτή είναι η βάση επιθέσεων DNS και ARP spoofing, όπου ο χρήστης πληκτρολογεί τη σωστή διεύθυνση και προσγειώνεται στο αντίγραφο του επιτιθέμενου. Οι αμυντικές απαντήσεις ακολουθούν από τον μηχανισμό: παρακολούθησε την ακεραιότητα των `/etc/hosts` και `/etc/resolv.conf` σε servers, προτίμησε DNSSEC και DNS-over-HTTPS όπου το περιβάλλον τα υποστηρίζει, και αντιμετώπισε κάθε ορατή-από-χρήστη ανακατεύθυνση σε απρόσμενη διεύθυνση ως περιστατικό και όχι ως δυσλειτουργία.

## 2. Διαχείριση διεργασιών

Μια διεργασία (process) είναι απλώς ένα πρόγραμμα που τρέχει: ο πυρήνας το φόρτωσε στη μνήμη, του έδωσε αναγνωριστικό, το προγραμμάτισε σε CPU και του χρεώνει τους πόρους που χρησιμοποιεί. Σε laptop ενός χρήστη μπορεί να τρέχουν διακόσιες διεργασίες οποιαδήποτε στιγμή — οι περισσότερες daemons, υπηρεσίες παρασκηνίου χωρίς τερματικό — και σε server ο αριθμός είναι ακόμα μεγαλύτερος. Το να ξέρεις να τις δείχνεις, να διαβάζεις τι καταναλώνουν, να αποφασίζεις ποιες αξίζουν περισσότερο από το μηχάνημα, να σταματάς αυτές που πήγαν στραβά, και να μετακινείς αυτές που πρέπει να βγουν από τη μέση, είναι η διαφορά ανάμεσα στο να διαχειρίζεσαι σύστημα και στο να μαντεύεις. Για δουλειά ασφαλείας υπάρχει δεύτερος λόγος να μάθεις αυτή την ύλη, αφού οι ίδιες εντολές είναι ο τρόπος να βρεις τη διεργασία που ακούει σε πόρτα, να ταυτοποιήσεις ύποπτο daemon ανάμεσα σε νόμιμους, και να σταματήσεις agent antivirus που παρεμβαίνει σε εξουσιοδοτημένο έλεγχο.

### 2.1 `ps` — βλέποντας τις δικές σου διεργασίες

Το κύριο εργαλείο για να κοιτάς διεργασίες είναι το `ps`, συντομογραφία του *process status*. Πληκτρολογημένο χωρίς ορίσματα δείχνει τις διεργασίες που είναι προσαρτημένες στο τρέχον τερματικό και ανήκουν στον τρέχοντα χρήστη — πράγμα που κρατάει την έξοδο αρκετά σύντομη για να είναι χρήσιμη όσο μαθαίνεις.

```bash
root@kali:~# ps
    PID TTY          TIME CMD
   4122 pts/0    00:00:00 bash
   4188 pts/0    00:00:00 ps
```

Εμφανίζονται μόνο δύο διεργασίες, και αυτό δεν είναι λάθος: το `ps` τυπώνει τις διεργασίες που ανήκουν σε αυτή τη συνεδρία κελύφους — δηλαδή εσένα συν την ίδια την εντολή `ps`. Οι τρεις στήλες είναι το λεξιλόγιο πάνω στο οποίο χτίζει το υπόλοιπο της ενότητας. Το `PID` είναι το αναγνωριστικό διεργασίας — αριθμός που ο πυρήνας αποδίδει σε κάθε διεργασία που δημιουργεί και που είναι μοναδικός ανάμεσα στις διεργασίες που τρέχουν εκείνη τη στιγμή. Είναι η λαβή που χρησιμοποιείς για να επιθεωρήσεις, να ιεραρχήσεις ή να σκοτώσεις οτιδήποτε. Το `TTY` ονομάζει το τερματικό στο οποίο η διεργασία είναι προσαρτημένη (το `pts/0` είναι το πρώτο ψευδο-τερματικό, αυτό που σου δίνει ο εξομοιωτής τερματικού σου), και ένα `?` σε αυτή τη στήλη σημαίνει ότι η διεργασία δεν έχει καθόλου τερματικό — η υπογραφή ενός daemon. Το `TIME` είναι ο συνολικός χρόνος CPU που η διεργασία κατανάλωσε από τότε που ξεκίνησε, όχι ο χρόνος ρολογιού που υπάρχει — διάκριση που μετράει, γιατί μια διεργασία που τρέχει μια εβδομάδα και χρησιμοποίησε δύο δευτερόλεπτα CPU συμπεριφέρεται πολύ διαφορετικά από μία που χρησιμοποίησε δύο ώρες.

Δύο χρήσιμες παραλλαγές της βασικής εντολής αξίζει να δοκιμαστούν αμέσως. Το `ps -f` προσθέτει στήλη που δείχνει το αναγνωριστικό γονικής διεργασίας (PPID) και την πλήρη γραμμή εντολών — που ξεκινάει να απαντάει «ποιος το ξεκίνησε αυτό, και με τι ορίσματα;». Και το `ps -ef` — το στυλ System V που οι διαχειριστές άλλων Unix συστημάτων απλώνουν από συνήθεια — δείχνει κάθε διεργασία του συστήματος με την ίδια λεπτομέρεια. Πράγμα που μας φέρνει στην επόμενη εντολή.

### 2.2 `ps aux` — κάθε διεργασία, κάθε χρήστης

Το να τρέχεις `ps` με τις τρεις επιλογές BSD `aux` εμφανίζει όλες τις τρέχουσες διεργασίες όλων των χρηστών μαζί με τα νούμερα πόρων καθεμιάς. Αυτή είναι η πιο πληκτρολογημένη εντολή αυτής της ενότητας, και η γραμμή κεφαλίδας που τυπώνει αξίζει απομνημόνευσης.

```bash
root@kali:~# ps aux
USER         PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root           1  0.0  0.6 168412 12984 ?        Ss   09:41   0:04 /sbin/init splash
root           2  0.0  0.0      0     0 ?        S    09:41   0:00 [kthreadd]
root         812  0.0  0.1  15420  9216 ?        Ss   09:41   0:00 sshd: /usr/sbin/sshd -D [listener] 0 of 10-100 startups
root        1044  0.0  0.4 240128 34220 ?        Ssl  09:41   0:01 /usr/lib/snapd/snapd
www-data    1204  0.1  1.1 3310420 88144 ?       Ssl  09:44   0:06 python3 /opt/portal/app.py
student     3901  0.0  0.1  10344  5120 pts/0    Ss   10:12   0:00 -bash
student     4122  0.0  0.0  12440  4096 pts/0    R+   10:31   0:00 ps aux
```

Κάθε στήλη απαντάει διαφορετικό ερώτημα. Το `USER` είναι ο λογαριασμός ως τον οποίο τρέχει η διεργασία — το πρώτο πράγμα να ελέγξεις όταν αποφασίζεις τι επιτρέπεται να της κάνεις: μια διεργασία που ανήκει στον δικό σου χρήστη μπορεί να σηματοδοτηθεί από σένα, ενώ οποιουδήποτε άλλου θέλει root. Το `PID` είναι το αναγνωριστικό. Τα `%CPU` και `%MEM` είναι το ποσοστό συνολικής CPU και μνήμης που η διεργασία χρησιμοποιεί τώρα, και τα `VSZ` και `RSS` είναι τα νούμερα μνήμης σε kilobytes — το `VSZ` είναι το εικονικό μέγεθος του χώρου διευθύνσεων που η διεργασία έχει δεσμεύσει, ενώ το `RSS` είναι το resident set size, η μνήμη που έχει στ' αλήθεια σε φυσική RAM αυτή τη στιγμή. Το `VSZ` είναι συνήθως πολύ μεγαλύτερο από το `RSS` και είναι το πιο παραπλανητικό από τα δύο, γιατί η δέσμευση χώρου διευθύνσεων δεν κοστίζει τίποτα. Το `TTY` είναι το τερματικό, με `?` για daemons, και το `STAT` είναι σύντομος κωδικός που περιγράφει την κατάσταση της διεργασίας.

Οι κωδικοί `STAT` αξίζει να μαθευτούν γιατί σου λένε αν μια διεργασία είναι υγιής. Το `R` σημαίνει running ή runnable — πάνω στην CPU ή περιμένοντας τη σειρά της. Το `S` σημαίνει διακοπτόμενος ύπνος (interruptible sleep), η φυσιολογική κατάσταση διεργασίας που περιμένει κάτι όπως πακέτο δικτύου ή πλήκτρο· σχεδόν τα πάντα σε ήσυχο σύστημα είναι σε `S`. Το `D` είναι αδιακόπτος ύπνος (uninterruptible sleep), που συνήθως σημαίνει μπλοκαρισμένο σε δίσκο ή δικτυακό I/O — και μια διεργασία κολλημένη σε `D` δεν μπορεί να σκοτωθεί ούτε με `SIGKILL` γιατί δεν τρέχει κανέναν κώδικα που θα χειριζόταν το σήμα. Διάγνωση, όχι εμπόδιο. Το `T` σημαίνει σταματημένη — αυτό που αφήνει πίσω το `Ctrl+Z`. Το `Z` σημαίνει zombie: η διεργασία τελείωσε αλλά ο γονέας της δεν μάζεψε ακόμα την κατάσταση εξόδου της, οπότε μια γραμμή μένει στον πίνακα κάνοντας τίποτα. Τα zombies δεν καταναλώνουν CPU ούτε μνήμη πέρα από την καταχώριση πίνακα, δεν μπορούν να σκοτωθούν, και εξαφανίζονται όταν ο γονέας διαβάσει την κατάσταση εξόδου ή τερματίσει ο ίδιος.

Το `START` είναι η ώρα που η διεργασία ξεκίνησε, το `TIME` είναι αθροιστικός χρόνος CPU και το `COMMAND` είναι η γραμμή εντολών — με την επιπλέον λεπτομέρεια ότι μια εντολή τυλιγμένη σε αγκύλες στην αρχή είναι νήμα πυρήνα (kernel thread) και όχι διεργασία χρήστη. Γι' αυτό το `[kthreadd]` δεν έχει μνήμη ούτε τερματικό. Μερικές παραλλαγές κερδίζουν θέση στις σημειώσεις σου: το `ps aux --sort=-%mem | head` δείχνει τους μεγαλύτερους καταναλωτές μνήμης, το `ps -eo pid,ppid,user,%cpu,cmd --sort=-%cpu | head` διαλέγει τις στήλες που σε νοιάζουν και ταξινομεί κατά CPU, και το `ps -ef --forest` σχεδιάζει το δέντρο διεργασιών — δείχνοντας ποιος daemon γέννησε ποιον worker. Προβολή που μετατρέπει το «υπάρχουν δώδεκα διεργασίες nginx» σε «υπάρχει ένας master και έντεκα workers».

### 2.3 Φιλτράρισμα διεργασιών με όνομα

Ένα απασχολημένο μηχάνημα παράγει εκατοντάδες γραμμές από `ps aux` — οπότε στην πράξη φιλτράρεις. Η τεχνική είναι το pipe που εισήχθη στο Μέρος 1ο (ενότητα 4.7), εφαρμοζόμενο εδώ σε έξοδο διεργασιών, και δουλεύει ακριβώς όπως με κάθε άλλη εντολή: στέλνεις το `ps aux` στο `grep` και κρατάς τις γραμμές που αναφέρουν το πρόγραμμα που σε ενδιαφέρει. Εδώ ψάχνουμε την κονσόλα του metasploit, το `msfconsole`.

```bash
root@kali:~# ps aux | grep msfconsole
root        5210  1.3  2.4 612344 198772 pts/1   Sl+  10:33   0:02 ruby /usr/bin/msfconsole -q
root        5233  0.0  0.0  12440  4096 pts/1    S+   10:33   0:00 grep msfconsole
```

Επιστρέφουν δύο γραμμές, και το να καταλάβεις γιατί είναι μικρό αλλά γνήσια χρήσιμο μάθημα. Η πρώτη είναι η πραγματική διεργασία: ένας διερμηινέας Ruby που τρέχει το script `msfconsole`, καταναλώνοντας 1.3% CPU και περίπου 2.4% μνήμης. Η δεύτερη γραμμή είναι η ίδια η εντολή `grep`, που ταίριαξε τη δική της γραμμή εντολών — μόνιμο παρεμπίπτον αλίευμα που μπερδεύει αρχάριους να νομίζουν ότι υπάρχουν δύο διεργασίες. Οι στάνταρ τρόποι να το ξεφορτωθείς είναι να εξαιρείς τον όρο αναζήτησης από τα αποτελέσματα (`ps aux | grep msfconsole | grep -v grep`) ή να βάλεις σε αγκύλες έναν χαρακτήρα του μοτίβου (`ps aux | grep "[m]sfconsole"`), αφού η έκφραση αγκύλης ταιριάζει την πραγματική διεργασία αλλά δεν εμφανίζεται αυτούσια στη δική της γραμμή εντολών του grep.

Υπάρχει καλύτερο εργαλείο γι' αυτή τη δουλειά, και αξίζει να υιοθετηθεί ως προεπιλογή: το `pgrep` γράφτηκε για να απαντάει ακριβώς το ερώτημα «ποιες διεργασίες ταιριάζουν με αυτό το όνομα;» — οπότε δεν ταιριάζει τον εαυτό του και τυπώνει μόνο αναγνωριστικά από προεπιλογή.

```bash
root@kali:~# pgrep -a msfconsole
5210 ruby /usr/bin/msfconsole -q
root@kali:~# pgrep -u student -l bash
3901 bash
root@kali:~# pgrep -f "app.py"
1204
```

Η παράμετρος `-a` τυπώνει την πλήρη γραμμή εντολών δίπλα στο PID, η `-u` φιλτράρει κατά χρήστη, η `-l` τυπώνει μόνο το όνομα, και η `-f` ταιριάζει με ολόκληρη τη γραμμή εντολών αντί μόνο για το όνομα εκτελέσιμου — αυτό που χρειάζεσαι για οτιδήποτε ξεκίνησε ως `python3 /opt/portal/app.py`, γιατί το όνομα διεργασίας εκεί είναι μόνο `python3`. Ο σύντροφός του, το `pkill`, στέλνει σήμα σε κάθε διεργασία που ταιριάζει — και θα το χρησιμοποιήσουμε αργότερα σε αυτή την ενότητα αφού εισαχθεί η έννοια των σημάτων.

### 2.4 `top` — βρίσκοντας την πιο άπληστη διεργασία

Το `ps` σου δίνει στιγμιότυπο· το `top` σου δίνει ταινία. Η εντολή `top` εμφανίζει διεργασίες ταξινομημένες κατά κατανάλωση πόρων και ανανεώνει την εμφάνιση κάθε λίγα δευτερόλεπτα — πράγμα που την κάνει εργαλείο επιλογής όταν θέλεις να δεις τι κάνει ένα μηχάνημα τώρα: ποια διεργασία τρώει την CPU, αν το φορτίο ανεβαίνει, και πόση μνήμη μένει.

```bash
root@kali:~# top
top - 10:36:22 up 55 min,  1 user,  load average: 0.42, 0.31, 0.24
Tasks: 214 total,   1 running, 213 sleeping,   0 stopped,   0 zombie
%Cpu(s):  3.9 us,  1.0 sy,  0.0 ni, 94.8 id,  0.3 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :   3914.8 total,   2412.6 free,    681.0 used,    821.2 buff/cache
MiB Swap:   2048.0 total,   2047.7 free,      0.3 used.   2893.0 avail Mem 

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1204 www-data  20   0 3310420  88144  21412 S   4.3   2.2   0:06.42 python3
   1044 root      20   0  240128  34220  19840 S   0.7   0.9   0:01.19 snapd
   5210 root      20   0  612344 198772  42188 S   0.3   5.0   0:02.11 ruby
      1 root      20   0  168412  12984   9216 S   0.0   0.6   0:04.33 systemd
```

Οι πέντε γραμμές κεφαλίδας συνοψίζουν όλο το μηχάνημα και αξίζει να διαβάζονται πριν τη λίστα διεργασιών. Η πρώτη γραμμή δίνει την ώρα, το uptime, τον αριθμό συνδεδεμένων χρηστών και τους τρεις **μέσους όρους φόρτου** (load averages), που αναφέρουν τον μέσο αριθμό εκτελέσιμων διεργασιών του τελευταίου ενός, πέντε και δεκαπέντε λεπτών. Μέσος φόρτου πάνω από τον αριθμό πυρήνων CPU σημαίνει ότι δουλειά περιμένει στην ουρά — σε αυτή την εικονική μηχανή ισοδύναμου ενός πυρήνα, το 0.42 σημαίνει ότι το μηχάνημα είναι άνετο. Η δεύτερη γραμμή μετράει διεργασίες κατά κατάσταση, και κάθε μη μηδενικός μετρητής `zombie` ή `stopped` αξίζει παρακολούθηση. Η τρίτη γραμμή σπάει τον χρόνο CPU σε κατηγορίες: το `us` είναι δουλειά χώρου χρήστη, το `sy` δουλειά πυρήνα, το `id` αδράνεια, το `wa` χρόνος αναμονής σε I/O (ένα ανερχόμενο `wa` σημαίνει συνήθως αργό δίσκο), και το `st` χρόνος *κλεμμένος* από τον hypervisor — το νούμερο που σου λέει ότι άλλη εικονική μηχανή στον ίδιο host τρώει τη CPU σου. Η τέταρτη και πέμπτη γραμμή περιγράφουν μνήμη: συνολική, ελεύθερη, χρησιμοποιούμενη, και την cache σελίδων στο `buff/cache` — μνήμη που ο πυρήνας χρησιμοποιεί για cache αναγνώσεων δίσκου και θα την επιστρέψει ακαριαία αν εφαρμογή τη χρειαστεί. Το να διαβάζεις το `free` χωρίς να διαβάζεις το `buff/cache` είναι το κλασικό αρχάριο λάθος, αφού το Linux χρησιμοποιεί σκόπιμα αλλιώς-αδρανή RAM ως cache: μηχάνημα με σχεδόν καθόλου `free` μνήμη και μεγάλο `buff/cache` δουλεύει ακριβώς όπως σχεδιάστηκε.

Κάτω από την κεφαλίδα έρχεται η λίστα διεργασιών, που επαναλαμβάνει αρκετές στήλες `ps` με δύο προσθήκες. Το `PR` είναι η προτεραιότητα του πυρήνα και το `NI` η τιμή nice που συζητά η επόμενη υποενότητα — και τα δύο είναι στη λίστα γιατί είναι τα κουμπιά που γυρνάς όταν μια διεργασία χρειάζεται περισσότερη ή λιγότερη CPU από τις άλλες.

Το `top` είναι διαδραστικό, και μισή ντουζίνα πλήκτρα κουβαλούν το μεγαλύτερο μέρος της αξίας του: το `P` ταξινομεί κατά χρήση CPU (προεπιλογή), το `M` κατά μνήμη, το `k` ζητάει PID και σήμα ώστε να σκοτώσεις διεργασία χωρίς να βγεις από την εμφάνιση, το `r` ζητάει PID και νέα τιμή nice ώστε να ξανα-ιεραρχήσεις μία, το `1` απλώνει τη γραμμή CPU για να δείχνει κάθε πυρήνα ξεχωριστά, το `h` δείχνει την πλήρη βοήθεια, και το `q` βγαίνει. Αν προτιμάς να συλλάβεις την έξοδο αντί να την παρακολουθείς, το `top -b -n 1 | head -20` το τρέχει μία φορά σε batch mode και τυπώνει το αποτέλεσμα — η μορφή για script ή αναφορά. Και αν ξοδεύεις αρκετό χρόνο κάνοντας αυτό, εγκατέστησε το `htop`: είναι η ίδια πληροφορία με χρώμα, υποστήριξη ποντικιού και κυλιόμενες στήλες.

### 2.5 `nice` — ορισμός προτεραιότητας νέας διεργασίας

Σε μηχάνημα με περισσότερη δουλειά από CPU, ο χρονοπρογραμματιστής του πυρήνα αποφασίζει ποιος τρέχει — και παίρνει αυτή την απόφαση εν μέρει με βάση την **τιμή nice** κάθε διεργασίας: αριθμό από −20 έως 19 που εκφράζει πόσο πρόθυμη είναι η διεργασία να παραχωρεί τη σειρά της σε άλλες. Η κλίμακα τρέχει ανάποδα από τη διαίσθηση: το −20 είναι η υψηλότερη προτεραιότητα (λιγότερο ευγενικό, πιο απαιτητικό), το 19 η χαμηλότερη (εξαιρετικά ευγενικό, πάντα υποχωρεί), και η προεπιλογή είναι 0. Μια διεργασία που ξεκίνησε με `nice` κουβαλάει την τιμή που της έδωσες σε όλη της τη ζωή — γι' αυτό η ρύθμιση εφαρμόζεται κατά την εκκίνηση.

Η παράμετρος `-n` εισάγει την προσαρμογή, κι εδώ ο ssh-agent daemon ξεκινάει με ευγενέστερη-από-προεπιλογή τιμή −10 — δηλαδή πρέπει να προτιμάται από τον χρονοπρογραμματιστή.

```bash
root@kali:~# nice -n -10 /usr/bin/ssh-agent
SSH_AUTH_SOCK=/tmp/ssh-XXXXXXuP3n9g/agent.4412; export SSH_AUTH_SOCK;
SSH_AGENT_PID=4412; export SSH_AGENT_PID;
echo Agent pid 4412;
root@kali:~# ps -o pid,ni,cmd -C ssh-agent
    PID  NI CMD
   4412 -10 /usr/bin/ssh-agent
```

Το πρόγραμμα ξεκίνησε φυσιολογικά — αποδόθηκε αναγνωριστικό διεργασίας, και το κέλυφος τύπωσε τις μεταβλητές περιβάλλοντος που ένας καλών χρειάζεται για να μιλήσει στον agent. Η εντολή επαλήθευσης είναι το ενδιαφέρον κομμάτι: το `ps -o pid,ni,cmd -C ssh-agent` διαλέγει συγκεκριμένες στήλες και ονομάζει τη διεργασία να ταιριάξει, και η στήλη `NI` δείχνει `-10` — επιβεβαιώνοντας ότι το αίτημα προτεραιότητας έγινε δεκτό. Η `-C` (ταίριασμα με όνομα εντολής) είναι τακτοποιημένη εναλλακτική στο τελετουργικό grep-και-pipe της ενότητας 2.3, με την ευχάριστη ιδιότητα να μην ταιριάζει τον εαυτό της.

Ένας κανόνας δικαιωμάτων μετράει εδώ: οποιοσδήποτε χρήστης μπορεί να κάνει διεργασία *ευγενέστερη* (να ανεβάσει τον αριθμό της, να παραχωρεί περισσότερο), αλλά μόνο ο root μπορεί να τον κατεβάσει (να κάνει διεργασία πιο απαιτητική). Αν απλός χρήστης δοκιμάσει την παραπάνω εντολή, το κέλυφος απαντάει `nice: cannot set niceness: Permission denied` και καμία διεργασία δεν ξεκινάει. Αυτή η ασυμμετρία είναι σκόπιμη, γιατί όλο το νόημα του μηχανισμού είναι να προστατεύει διαδραστική δουλειά από το να λιμοκτονεί εξαιτίας εργασιών παρασκηνίου — και θα νικιόταν αν οποιοσδήποτε χρήστης μπορούσε να διεκδικήσει την αρχή της ουράς.

Η μη προνομιούχα και πολύ πιο συνηθισμένη χρήση είναι η αντίστροφη κατεύθυνση — να σπρώχνεις μια μακριά, ασήμαντη δουλειά έξω από τη μέση ώστε να μην ανταγωνίζεται τη δουλειά που κάνεις στ' αλήθεια:

```bash
root@kali:~# nice -n 19 ./backup-script.sh &
[1] 5487
root@kali:~# nice -n 19 /usr/bin/updatedb &
[2] 5490
```

Και οι δύο δουλειές τρέχουν στη χαμηλότερη δυνατή προτεραιότητα, και οι αριθμοί εργασίας `[1]` και `[2]` με τα PIDs μετά τους είναι η επιβεβαίωση του κελύφους — το θέμα της ενότητας 2.8. Αυτό το μοτίβο αξίζει να θυμάσαι, γιατί το «τρέξε αυτό στο παρασκήνιο με ελάχιστη προτεραιότητα» είναι το σωστό σχήμα για σχεδόν κάθε εργασία συντήρησης σε μηχάνημα που κάποιος άλλος χρησιμοποιεί.

### 2.6 `renice` — αλλαγή προτεραιότητας τρέχουσας διεργασίας

Η προτεραιότητα διεργασίας που ήδη τρέχει μπορεί να αλλάξει χωρίς επανεκκίνηση, με το `renice`. Παίρνει τιμή nice ή προσαρμογή και ένα ή περισσότερα PIDs, και δουλεύει σε διεργασίες που δεν ξεκίνησες εσύ — αρκεί να έχεις τα προνόμια να τις αλλάξεις.

```bash
root@kali:~# renice 20 6242
6242 (process ID) old priority 0, new priority 20
root@kali:~# ps -o pid,ni,cmd -p 6242
    PID  NI CMD
   6242  20 /usr/bin/updatedb
root@kali:~# renice -n -5 -p 6242
renice: failed to set priority for 6242 (process ID): Permission denied
```

Η γραμμή αναφοράς είναι ξεκάθαρη και ονομάζει και τις δύο τιμές — πράγμα που κάνει το `renice` ευχάριστα αυτο-τεκμηριωμένο: η διεργασία πήγε από τιμή nice 0 σε 20, δηλαδή υποχωρεί πια σε όλα τα άλλα στο μηχάνημα. Ένα μεταγενέστερο `ps` επιβεβαιώνει τη νέα τιμή. Η τρίτη εντολή δείχνει τον κανόνα δικαιωμάτων της προηγούμενης υποενότητας από την άλλη μεριά: ως μη προνομιούχος χρήστης, το να κατεβάσεις την τιμή nice (εδώ σε −5, που θα ανέβαζε την προτεραιότητα της διεργασίας) απορρίπτεται κατά μέτωπο, με τη διεργασία να μένει στην προηγούμενη τιμή της.

Τρεις μορφές αξίζει να κρατήσεις στις σημειώσεις σου. Το `renice -n 10 -p 6242` ορίζει απόλυτη τιμή με τις ρητές παραμέτρους — η μορφή να προτιμάς σε scripts γιατί είναι ξεκάθαρη. Το `renice -u student` αλλάζει την προτεραιότητα κάθε διεργασίας που ανήκει σε χρήστη — καλός τρόπος να ησυχάσεις έναν ξέφρενο λογαριασμό χτισίματος χωρίς να κυνηγάς PIDs. Και το `renice 5 -g developers` εφαρμόζεται σε ομάδα διεργασιών. Σε σύγχρονο μηχάνημα systemd υπάρχει δεύτερος, συμπληρωματικός μηχανισμός — τα cgroups και οι εντολές `systemd-run --slice` και `systemctl set-property` σε αφήνουν να βάλεις ταβάνι CPU και μνήμης για ολόκληρη υπηρεσία αντί απλώς να υποδεικνύεις στον χρονοπρογραμματιστή. Αυτή είναι η προσέγγιση να χρησιμοποιείς όταν η απαίτηση είναι «αυτή η υπηρεσία δεν επιτρέπεται ποτέ να χρησιμοποιεί πάνω από έναν πυρήνα» αντί για «αυτή η υπηρεσία πρέπει να είναι ευγενική».

### 2.7 `kill` — σταμάτημα διεργασιών με σήματα

Η εντολή `kill` σταματάει διεργασίες, και το όνομά της παραπλανά με χρήσιμο τρόπο: αυτό που στέλνει στ' αλήθεια είναι *σήμα* — αριθμημένη, ασύγχρονη ειδοποίηση που παραδίδεται σε διεργασία από τον πυρήνα. Και η διεργασία μπορεί να χειρίζεται τα περισσότερα σήματα όπως θέλει: να καθαρίζει, να σώζει κατάσταση, να κλείνει sockets, να τα αγνοεί ή να τερματίζει. Υπάρχουν 64 σήματα συνολικά, και τα δύο που μετράνε περισσότερο είναι το ευγενικό και το μοιραίο. Εδώ στέλνεται στη διεργασία με PID 6242 το σήμα νούμερο 1.

```bash
root@kali:~# kill -1 6242
root@kali:~# ps -p 6242
    PID TTY          TIME CMD
root@kali:~# kill -l
 1) SIGHUP	 2) SIGINT	 3) SIGQUIT	 4) SIGILL	 5) SIGTRAP
 6) SIGABRT	 7) SIGBUS	 8) SIGFPE	 9) SIGKILL	10) SIGUSR1
11) SIGSEGV	12) SIGUSR2	13) SIGPIPE	14) SIGALRM	15) SIGTERM
...
root@kali:~# kill -9 4378
```

Το `SIGHUP`, σήμα 1, σήμαινε αρχικά «το τερματικό στο οποίο ήσουν συνδεδεμένος έκλεισε» — και daemons όπως τα `sshd`, `nginx` και `rsyslog` το επανερμηνεύουν ως «ξαναδιάβασε τα αρχεία ρυθμίσεών σου και ξανάνοιξε τα αρχεία log σου». Γι' αυτό το `kill -1` είναι ο παραδοσιακός τρόπος να κάνεις υπηρεσία να ξαναφορτώνει χωρίς να ρίχνει τις συνδέσεις της, και γιατί το ίδιο σήμα τερματίζει απλό πρόγραμμα προσκηνίου που δεν έχει χειριστή γι' αυτό. Επειδή το `updatedb` είναι βραχύβιο πρόγραμμα χωρίς χειριστή, το να του στείλεις `SIGHUP` το τελείωσε, και το `ps` που ακολουθεί δείχνει άδειο πίνακα.

Το `kill -l` δείχνει κάθε σήμα που το σύστημα γνωρίζει, και οι αριθμοί αξίζει να μαθευτούν σε ζευγάρια. Το σήμα 15, `SIGTERM`, είναι η *προεπιλογή* όταν πληκτρολογείς `kill` χωρίς αριθμό, και είναι η σωστή πρώτη απόπειρα για κάθε διεργασία: ζητάει ευγενικά από το πρόγραμμα να τερματίσει, και ένα καλογραμμένο πρόγραμμα θα αδειάσει τα buffers του, θα αφαιρέσει τα προσωρινά του αρχεία και θα κλείσει τα sockets του φεύγοντας. Το σήμα 9, `SIGKILL`, δεν μπορεί να πιαστεί, να μπλοκαριστεί ή να αγνοηθεί — ο πυρήνας αφαιρεί τη διεργασία επιτόπου. Είναι το σωστό εργαλείο για διεργασία που αγνόησε το `SIGTERM` και λάθος εργαλείο για όλα τα άλλα, γιατί το `SIGKILL` δεν δίνει στο πρόγραμμα καμία ευκαιρία να καθαρίσει — έτσι διαφθείρονται βάσεις δεδομένων και μένουν πίσω μπαγιάτικα αρχεία κλειδώματος. Το σήμα 2, `SIGINT`, είναι αυτό που στέλνει το `Ctrl+C` από το τερματικό· το σήμα 3, `SIGQUIT`, είναι το `Ctrl+\`· το σήμα 18 σταματάει διεργασία και το 19 τη συνεχίζει — αυτό που κάνουν τα `Ctrl+Z` και `bg` από κάτω.

Αυτή η σειρά — `SIGTERM` πρώτα, μετά κλιμάκωση — είναι η επαγγελματική συνήθεια και αξίζει να την επιβάλλεις στον εαυτό σου από την πρώτη μέρα. Μια διεργασία που δεν πεθαίνει σε `SIGTERM` σου λέει κάτι: μπορεί να είναι μπλοκαρισμένη σε αδιακόπτο I/O, μπορεί να είναι zombie, ή μπορεί να αγνοεί σκόπιμα το σήμα — και καθένα από αυτά αξίζει μια στιγμή σκέψης πριν απλώσεις το χέρι στο `-9`. Γρήγορος έλεγχος λογικής για την περίπτωση zombie είναι το `ps -o pid,stat,cmd -p <pid>`, όπου ένα `Z` στη στήλη κατάστασης σημαίνει ότι κανένα σήμα δεν θα δουλέψει ποτέ — γιατί δεν έχει μείνει τρέχουσα διεργασία να το λάβει.

Δύο συγγενικές εντολές κάνουν το στοχευμένο σκότωμα ευκολότερο. Το `pkill` στέλνει σήμα σε κάθε διεργασία που ταιριάζει με μοτίβο — οπότε το `pkill -f app.py` σταματάει την web εφαρμογή με βάση τη γραμμή εντολών της και το `pkill -u student -TERM -f backup` σταματάει τις εργασίες backup ενός χρήστη χωρίς να αγγίζει τίποτα άλλο. Το `killall` κάνει το ίδιο με ακριβές όνομα προγράμματος. Και τα δύο είναι αρκετά ισχυρά για να είναι επικίνδυνα — ένα μοτίβο πολύ φαρδύ θα ταιριάξει κάτι που δεν σκόπευες, και το `pkill -9 -f python` σε απασχολημένο μηχάνημα βγάζει νοκ-άουτ μια ντουζίνα αθώες διεργασίες. Οπότε η ασφαλής ροή είναι πάντα να τρέχεις `pgrep` πρώτα, να κοιτάς τι θα επηρεαζόταν, και μόνο μετά να στέλνεις το σήμα με το ίδιο μοτίβο.

### 2.8 Εργασίες παρασκηνίου, `jobs`, `fg` και `nohup`

Μια εντολή πληκτρολογημένη σε prompt κατέχει το τερματικό μέχρι να τελειώσει — άβολο τη στιγμή που ξεκινάς κάτι μακροχρόνιο. Το κέλυφος παρέχει **έλεγχο εργασιών** (job control) ακριβώς γι' αυτό το πρόβλημα: το να προσαρτήσεις ένα σύμβολο `&` σε εντολή την τρέχει στο παρασκήνιο, επιστρέφοντας αμέσως το prompt σου ενώ η διεργασία συνεχίζει να δουλεύει.

```bash
root@kali:~# nano lab-notes.txt &
[1] 4312
root@kali:~# jobs
[1]+  Stopped                 nano lab-notes.txt
root@kali:~# fg %1
```

Το κέλυφος απάντησε με τον αριθμό εργασίας `[1]` και το αναγνωριστικό διεργασίας `4312`, και σε εφαρμογή τερματικού εδώ εμφανίζεται μια σημαντική λεπτομέρεια. Το `nano` είναι διαδραστικό πρόγραμμα πλήρους οθόνης, και πρόγραμμα αυτής της κατηγορίας κανονικά *σταματάει μόνο του* όταν βρεθεί στο παρασκήνιο χωρίς τερματικό — αυτό δείχνει η έξοδος `jobs`: η εργασία φαίνεται ως `Stopped` και όχι `Running`, γιατί ο editor προσπάθησε να διαβάσει από τερματικό που δεν ελέγχει πια. Αυτός είναι ο γενικός κανόνας και αξίζει να εμπεδωθεί: το παρασκήνιο είναι για προγράμματα που δεν χρειάζονται το πληκτρολόγιό σου — όπως μεταγλωττιστής, λήψη, σάρωση ή μακριά αντιγραφή — όχι για διαδραστικούς editors.

```bash
root@kali:~# ./backup-script.sh &
[2] 4701
root@kali:~# jobs -l
[1]+  4312 Stopped                 nano lab-notes.txt
[2]-  4701 Running                 ./backup-script.sh &
root@kali:~# bg %1
```

Με γνήσια μη διαδραστικό πρόγραμμα η συμπεριφορά είναι αυτή που θα ήλπιζες: η εργασία `[2]` είναι `Running`, και το `jobs -l` δείχνει και τις δύο εργασίες με τα PIDs τους και — σημαντικά — το σημάδι στη δεύτερη στήλη. Το `+` σημαδεύει την *τρέχουσα* εργασία, αυτήν στην οποία τα `fg` και `bg` ενεργούν όταν δεν ονομάζεις μία, ενώ το `-` σημαδεύει την προηγούμενη εργασία· γι' αυτό το σκέτο `fg` συνεχίζει ό,τι στάλθηκε πιο πρόσφατα στο παρασκήνιο, και γιατί είναι ασφαλέστερο να ονομάζεις την εργασία ρητά μέχρι η ιδέα να γίνει δεύτερη φύση.

Το πλήρες λεξιλόγιο ελέγχου εργασιών είναι μικρό. Το `Ctrl+Z` *σταματάει* τη διεργασία προσκηνίου και σε επιστρέφει στο prompt — παύση και όχι έξοδος. Το `bg %1` συνεχίζει τη σταματημένη εργασία `1` στο παρασκήνιο. Το `fg %1` τη φέρνει πίσω στο προσκήνιο, και τότε κατέχει πάλι το τερματικό. Το `jobs` τις δείχνει, το `kill %1` στέλνει σήμα σε εργασία με αριθμό αντί για PID, και το `disown %1` αφαιρεί εργασία από τον πίνακα του κελύφους ώστε να μη στέλνεται `SIGHUP` όταν το κέλυφος βγαίνει.

Αυτό το τελευταίο εξηγεί τον πιο συνηθισμένο τρόπο που οι άνθρωποι χάνουν δουλειά. Όταν ένα τερματικό κλείνει, το κέλυφος στέλνει `SIGHUP` στις εργασίες του, και κάθε διεργασία που δεν το χειρίζεται πεθαίνει — οπότε μια λήψη ξεκινημένη με σκέτο `&` σε παράθυρο τερματικού που μετά κλείνεις απλώς εξαφανίζεται. Η παραδοσιακή άμυνα είναι το `nohup`, που αποσυνδέει τη διεργασία από το σήμα hangup και ανακατευθύνει την έξοδό της — γιατί δεν υπάρχει πια τερματικό να τυπώσει:

```bash
root@kali:~# nohup ./scan.sh > scan.log 2>&1 &
[3] 4820
root@kali:~# ps -o pid,stat,cmd -p 4820
    PID STAT CMD
   4820 S    /bin/bash ./scan.sh
root@kali:~# nohup ./scan.sh &
[4] 4833
nohup: ignoring input and appending output to 'nohup.out'
```

Η ανακατεύθυνση `> scan.log 2>&1` στέλνει και standard έξοδο και standard error σε αρχείο — γι' αυτό η πρώτη κλήση είναι σιωπηλή. Παράλειψέ την, όπως στη δεύτερη κλήση, και το `nohup` γράφει την έξοδο στο `nohup.out` στον τρέχοντα κατάλογο και το λέει — το μήνυμα εμφανίζεται στο τερματικό σου *μετά* τη γραμμή εργασίας γιατί γράφεται στο standard error ενώ το κέλυφος τυπώνει ακόμα τον αριθμό εργασίας. Η διεργασία επιζεί πια του τερματικού, και η στήλη `STAT` τη δείχνει να κοιμάται φυσιολογικά. Για οτιδήποτε θέλεις να επιστρέψεις, ένας πολυπλέκτης τερματικού όπως `tmux` ή `screen` είναι το καλύτερο εργαλείο, γιατί κρατάει ολόκληρη συνεδρία ζωντανή στον server και σε αφήνει να ξανασυνδεθείς σε αυτήν από οπουδήποτε, με scrollback και πολλά παράθυρα· το `nohup` μένει η ελαφριά απάντηση όταν χρειάζεσαι μόνο μία εντολή να επιζήσει της συνεδρίας σου.

### 2.9 Προγραμματισμός διεργασίας με `at`

Μερικές φορές η σωστή στιγμή να τρέξει μια δουλειά είναι στο μέλλον. Η εντολή `at` προγραμματίζει μια εντολή να τρέξει **μία φορά**, σε καθορισμένη ώρα, και είναι το εργαλείο στο οποίο απλώνεις το χέρι όταν θέλεις εργασία να γίνει αφού φύγεις σπίτι ή αφού συμβεί κάποιο άλλο γεγονός. Διαβάζει τις εντολές να τρέξει από την standard είσοδο — γι' αυτό η κλήση φαίνεται διαδραστική.

```bash
root@kali:~# at 9:00pm
warning: commands will be executed using /bin/sh
at> /root/simple_bash.sh
at> <EOT>
job 3 at Sat Oct 10 21:00:00 2026
```

Η πρώτη γραμμή είναι προειδοποίηση και όχι παράπονο, και αξίζει να την ακούς: το `at` τρέχει τις εντολές του με `/bin/sh`, όχι με το διαδραστικό σου κέλυφος — οπότε οτιδήποτε εξαρτάται από σύνταξη ειδική του bash, aliases ή μεταβλητές περιβάλλοντός σου δεν θα δουλέψει. Γράψε τη δουλειά όπως θα έγραφες script, με πλήρεις διαδρομές. Το prompt `at>` μετά δέχεται εντολές μία ανά γραμμή, και το πάτημα `Ctrl+D` — που το κέλυφος εμφανίζει ως `<EOT>`, για end of transmission — τελειώνει τη δουλειά. Η γραμμή επιβεβαίωσης αναφέρει τον αριθμό εργασίας και την ακριβή ώρα που θα τρέξει, και το `at` ερμηνεύει ποικιλία ανθρώπινων μορφών: `at 9:00pm`, `at 14:30`, `at now + 10 minutes`, `at midnight`, `at 09:00 tomorrow`. Ώρες χωρίς ημερομηνία λαμβάνονται ως σήμερα αν είναι ακόμα στο μέλλον και αλλιώς αύριο — που καμιά φορά εκπλήσσει κόσμο στις 23:59.

Η ουρά εκκρεμών εργασιών διαχειρίζεται με τρεις σύντομες εντολές. Το `atq` τις δείχνει, το `at -c <εργασία>` τυπώνει ολόκληρο το περιβάλλον και την εντολή που μια προγραμματισμένη εργασία θα τρέξει — ο οριστικός τρόπος να αποσφαλματώσεις μία που συμπεριφέρεται άσχημα — και το `atrm <εργασία>` την αφαιρεί. Η υπηρεσία πίσω από την εντολή είναι daemon που λέγεται `atd`, και σε ελάχιστο σύστημα μπορεί να μην τρέχει· το `systemctl status atd` θα το πει, και το `systemctl enable --now atd` το φτιάχνει. Η πρόσβαση στο `at` ελέγχεται από τα `/etc/at.allow` και `/etc/at.deny` — το ίδιο μοτίβο allow-and-deny που χρησιμοποιεί το `cron`. Έτσι οι διαχειριστές κρατούν απλούς χρήστες από το να προγραμματίζουν δουλειά σε παραγωγικά μηχανήματα.

Για δουλειές που πρέπει να τρέχουν **επαναλαμβανόμενα** — κάθε βράδυ, κάθε ώρα, κάθε Δευτέρα — το εργαλείο είναι το `cron` και όχι το `at`, και η διαφορά αξίζει να ειπωθεί καθαρά: το `at` είναι για εφάπαξ, το `cron` για επανάληψη. Οι προγραμματισμένες δουλειές ενός χρήστη ζουν σε crontab, που επεξεργάζεται με `crontab -e`, και κάθε γραμμή περιέχει πέντε πεδία χρόνου και μετά την εντολή να τρέξει:

```bash
root@kali:~# crontab -l
# m h  dom mon dow   command
  0 3  *   *   *     /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
 30 1  *   *   0     /usr/local/bin/weekly-report.sh
```

Διαβάζοντας τα πεδία με σειρά: λεπτό, ώρα, μέρα μήνα, μήνας, μέρα εβδομάδας, όπου το `*` σημαίνει «κάθε». Άρα η πρώτη γραμμή τρέχει το backup στις 03:00 κάθε μέρα, και η δεύτερη τρέχει την εβδομαδιαία αναφορά στις 01:30 κάθε Κυριακή (μέρα-εβδομάδας 0). Τα ισοδύναμα σε επίπεδο συστήματος ζουν στα `/etc/crontab` και `/etc/cron.d/`, με την προσθήκη πεδίου χρήστη, ενώ οι κατάλογοι `/etc/cron.hourly`, `/etc/cron.daily`, `/etc/cron.weekly` και `/etc/cron.monthly` δέχονται σκέτα scripts χωρίς καθόλου πεδία χρόνου. Οι σύγχρονες διανομές χρησιμοποιούν ολοένα systemd timers αντί γι' αυτό — που προσφέρουν ίδιο προγραμματισμό με καλύτερη καταγραφή και ικανότητα να πυροδοτούνται από γεγονότα και όχι μόνο από ρολόι. Το `systemctl list-timers` δείχνει τι είναι προγραμματισμένο σε τέτοιο σύστημα.

Για δουλειά ασφαλείας, οι προγραμματισμένες δουλειές μετράνε για δύο λόγους. Αμυντικά, το `cron` είναι κλασικός μηχανισμός επιμονής (persistence) — οπότε οτιδήποτε προγραμματισμένο δεν αναγνωρίζεις αξίζει προσοχή: μια δουλειά που κατεβάζει και τρέχει script, ή που επανεμφανίζεται αφού αφαιρεθεί, είναι εύρημα. Επιθετικά, το `at` είναι ο αξιόπιστος τρόπος να προγραμματίσεις επαναφορά όταν πρόκειται να κάνεις αλλαγή που μπορεί να κόψει τη δική σου πρόσβαση — επαναφόρτωση firewall, αναδιαμόρφωση δικτύου, επανεκκίνηση SSH daemon — αφού μια δουλειά οπλισμένη πριν την αλλαγή θα επαναφέρει την παλιά κατάσταση ακόμα κι αν η συνεδρία σου πεθάνει μαζί της. Αυτή η μία τεχνική έχει διασώσει περισσότερες συνεδρίες απομακρυσμένης διαχείρισης από οποιαδήποτε άλλη συνήθεια αυτής της ενότητας.

## 3. Μεταβλητές περιβάλλοντος χρήστη

Οι μεταβλητές είναι απλώς ονοματισμένες τιμές — ζευγάρια κλειδιού-τιμής που κρατάει ένα τρέχον κέλυφος. Και το να τις καταλάβεις είναι απαραίτητο για να βγάλεις το μέγιστο από σύστημα Linux, γιατί μεγάλο μέρος όσων το κέλυφος και τα προγράμματα που ξεκινάει θεωρούν «το περιβάλλον» δεν είναι τίποτα παραπάνω από μια λίστα τους. Υπάρχουν δύο οικογένειες, και η διάκριση μετράει. Μια **μεταβλητή κελύφους** (shell variable) υπάρχει μόνο μέσα στο κέλυφος που τη δημιούργησε· είναι αόρατη στα προγράμματα που το κέλυφος ξεκινάει. Μια **μεταβλητή περιβάλλοντος** (environment variable) έχει *εξαχθεί* (export), που σημαίνει ότι αντιγράφεται στο περιβάλλον κάθε θυγατρικής διεργασίας — άρα σε κάθε πρόγραμμα που τρέχεις από αυτό το κέλυφος και κάθε διεργασία που αυτά τα προγράμματα ξεκινούν με τη σειρά τους. Οι μεταβλητές κληρονομούνται κάτω στο δέντρο διεργασιών και δεν ρέουν ποτέ πίσω πάνω — πράγμα που εξηγεί το μεγαλύτερο μέρος της μπερδεμένης συμπεριφοράς που συναντούν αρχάριοι: μια θυγατρική διεργασία μπορεί να διαβάσει ό,τι εξήγαγες, αλλά δεν μπορεί να αλλάξει ό,τι βλέπει ο γονέας της.

Η σύμβαση για ονόματα είναι κεφαλαία — `HOME`, `PATH`, `USER` — που είναι σύμβαση και όχι κανόνας, αλλά πολύτιμη: γιατί τα `HISTSIZE` και `histsize` είναι δύο εντελώς διαφορετικές μεταβλητές και μόνο η μία είναι αυτή που το κέλυφος χρησιμοποιεί.

### 3.1 Βλέποντας όλες τις μεταβλητές

Δύο εντολές δείχνουν μεταβλητές, και η διαφορά τους είναι η παραπάνω διάκριση σε σκυρόδεμα. Το `set`, πληκτρολογημένο χωρίς ορίσματα, τυπώνει κάθε μεταβλητή και συνάρτηση κελύφους που το τρέχον κέλυφος γνωρίζει, συμπεριλαμβανομένων όλων των μεταβλητών περιβάλλοντος που κληρονόμησε. Το `env` τυπώνει μόνο το εξαχθέν περιβάλλον — τη λίστα που οι θυγατρικές διεργασίες θα λάβουν στ' αλήθεια.

```bash
root@kali:~# set | more
BASH=/usr/bin/bash
BASHOPTS=checkwinsize:cmdhist:complete_fullquote:expand_aliases:extquote:force_fignore:globasciiranges
BASH_ALIASES=()
BASH_ARGC=()
BASH_ARGV=()
BASH_CMDS=()
BASH_COMPLETION_VERSINFO=([0]="2" [1]="11")
BASH_LINENO=()
BASH_SOURCE=()
...
COLUMNS=80
DIRSTACK=()
EUID=0
GROUPS=([0]="0")
HISTFILE=/root/.bash_history
HISTFILESIZE=2000
HISTSIZE=1000
HOME=/root
HOSTNAME=kali
--More--
```

Το pipe στο `more` δεν είναι προαιρετικό στην πράξη: σε φυσιολογικό desktop το `set` τυπώνει εκατοντάδες γραμμές, οι περισσότερες εσωτερικές μεταβλητές κελύφους όπως το `BASH_ARGC` που δεν θα χρησιμοποιήσεις ποτέ. Μέσα στον θόρυβο, μια χούφτα γνώριμα ονόματα εμφανίζονται — το `HOME` είναι ο προσωπικός σου κατάλογος, το `HOSTNAME` το όνομα του μηχανήματος, το `HISTFILE` το αρχείο όπου γράφεται το ιστορικό εντολών σου, και το `HISTSIZE` ο αριθμός εντολών που το κέλυφος κρατάει στη μνήμη για να σου προσφέρει όταν πατάς το πάνω βελάκι. Επειδή η έξοδος είναι συνηθισμένο κείμενο που πάει στην standard έξοδο, μπορεί να φιλτραριστεί, να ταξινομηθεί και να διπλωθεί όπως οτιδήποτε άλλο — ακριβώς αυτό που κάνει η επόμενη υποενότητα.

### 3.2 Φιλτράρισμα για συγκεκριμένη μεταβλητή

Το να στέλνεις το `set` στο `grep` με pipe είναι ο τρόπος να βρεις μία μεταβλητή ανάμεσα σε εκατοντάδες, και η τεχνική είναι πανομοιότυπη με το φιλτράρισμα διεργασιών της ενότητας 2.3. Εδώ ψάχνουμε για το `HISTSIZE`.

```bash
root@kali:~# set | grep HISTSIZE
HISTFILESIZE=2000
HISTSIZE=1000
root@kali:~# echo "my history holds $HISTSIZE commands"
my history holds 1000 commands
root@kali:~# printenv HISTSIZE

root@kali:~# printenv HOME
/root
```

Τρεις εντολές, και η σιωπή της τρίτης είναι το πιο διδακτικό πράγμα αυτής της υποενότητας. Η προσέγγιση `grep` τυπώνει και τις δύο μεταβλητές σχετικές με ιστορικό στη μορφή `όνομα=τιμή` που το κέλυφος τις κρατάει, και η μορφή `echo` ενσωματώνει την τιμή σε πρόταση ενώ εισάγει το σύμβολο που μετράει: το **`$` πριν από όνομα σημαίνει «αντικατάστησε την τιμή»**. Παράλειψε το δολάριο και τυπώνεις τα γράμματα του ονόματος πίσω στον εαυτό σου — το πιο συνηθισμένο λάθος ολόκληρης αυτής της ενότητας.

Το `printenv` τυπώνει *μόνο την τιμή* μιας μεταβλητής — αυτό που θέλεις μέσα σε script. Και εδώ δεν τύπωσε απολύτως τίποτα. Αυτό δεν είναι λάθος: το `HISTSIZE` είναι ορισμένο, όπως οι δύο πρώτες εντολές αποδεικνύουν, αλλά δεν έχει **εξαχθεί** ποτέ — οπότε υπάρχει μόνο μέσα σε αυτό το κέλυφος και η διεργασία `printenv`, παιδί του κελύφους, δεν μπορεί να το δει. Η κατάσταση εξόδου λέει την ίδια ιστορία, επιστρέφοντας 1 για μεταβλητή που δεν είναι στο περιβάλλον. Το `printenv HOME` δουλεύει, και τυπώνει `/root`, γιατί το `HOME` *είναι* εξαχθέν και παραδίδεται σε κάθε διεργασία που το κέλυφος ξεκινάει. Δεν υπάρχει καλύτερη επίδειξη της διαφοράς ανάμεσα σε μεταβλητή κελύφους και μεταβλητή περιβάλλοντος, και εξηγεί τη συμπεριφορά κάθε προγράμματος για το οποίο θα αναρωτηθείς ποτέ: αν ένα εργαλείο ισχυρίζεται ότι δεν ξέρει τιμή που είναι φανερά ορισμένη στο τερματικό σου, η μεταβλητή δεν εξήχθη ποτέ.

Άρα η απάντηση στο αρχικό ερώτημα είναι ότι αυτό το κέλυφος θυμάται χίλιες εντολές. Αυτό είναι άνετο για διαδραστική δουλειά, και είναι επίσης γεγονός με επιπτώσεις ασφαλείας που αξίζει να σημειωθούν: το αρχείο ιστορικού σου είναι καταγραφή όσων πληκτρολόγησες — συμπεριλαμβανομένων κωδικών περασμένων ως ορίσματα γραμμής εντολών και hosts στους οποίους συνδέθηκες. Γι' αυτό το `~/.bash_history` είναι ανάμεσα στα πρώτα αρχεία που ένας επιτιθέμενος διαβάζει σε παραβιασμένο μηχάνημα — και γιατί το να το καθαρίζεις, ή να απενεργοποιείς ιστορικό για ευαίσθητες εντολές με αρχικό κενό, είναι μέρος της ρουτίνας ενός χειριστή.

### 3.3 Αλλαγή τιμής προσωρινά

Το να αλλάξεις μεταβλητή είναι θέμα να της αποδώσεις νέα τιμή, και η απόδοση γράφεται χωρίς κενά γύρω από το ίσον.

```bash
root@kali:~# HISTSIZE=0
root@kali:~# echo $HISTSIZE
0
root@kali:~# echo $HISTSIZE > ~/valueofHISTSIZE.txt
root@kali:~# cat ~/valueofHISTSIZE.txt
0
```

Η πρώτη γραμμή ορίζει τη μεταβλητή σε μηδέν και η δεύτερη το επιβεβαιώνει — και το αποτέλεσμα είναι ακριβώς αυτό που αυτή η τιμή υπονοεί: το κέλυφος δεν κρατάει πια καμία εντολή στη μνήμη για την τρέχουσα συνεδρία, οπότε το πάτημα του πάνω βελάκου δεν παράγει τίποτα και η ανάκληση ιστορικού σταματάει να δουλεύει μέχρι να αλλάξεις την τιμή πίσω. Είναι μικρή επίδειξη μιας μεγάλης αλήθειας για ρυθμίσεις: ότι μια αθώα μονοχαρακτηρική αλλαγή αφαιρεί σιωπηλά μια ευκολία στην οποία βασίζεσαι, χωρίς κανένα μήνυμα σφάλματος.

Δύο λεπτομέρειες σε αυτό το transcript αξίζει να σταθούμε, γιατί είναι εκεί που οι αρχάριοι χάνουν χρόνο. Η πρώτη είναι ο κανόνας κενού: το `HISTSIZE=0` αποδίδει, ενώ το `HISTSIZE = 0` ερμηνεύεται από το κέλυφος ως απόπειρα να τρέξει εντολή που λέγεται `HISTSIZE` με δύο ορίσματα — που αποτυγχάνει με `HISTSIZE: command not found`. Το ίσον πρέπει να είναι κολλημένο στο όνομα και στην τιμή, και καμία άλλη διάταξη δεν δουλεύει. Η δεύτερη λεπτομέρεια είναι η ανακατεύθυνση στην τρίτη εντολή. Η πρόθεση — και συνήθεια που αξίζει να υιοθετήσεις — είναι να *σώσεις την παλιά τιμή κάπου πριν την αλλάξεις*, ώστε να μπορείς πάντα να επαναφέρεις τα πράγματα: το `echo $HISTSIZE > ~/valueofHISTSIZE.txt` γράφει την τρέχουσα τιμή σε αρχείο στον προσωπικό σου κατάλογο, και το `cat` επιβεβαιώνει τι γράφτηκε. Πρόσεξε το `>`, που στέλνει την έξοδο στο αρχείο· χωρίς αυτό, η εντολή θα τύπωνε την τιμή στο τερματικό και δεν θα έσωζε τίποτα — λάθος εύκολο να γίνει και εύκολο να εντοπιστεί, αφού η ανακατεύθυνση δημιουργεί το αρχείο ως παρενέργεια. Σε αυτή την περίπτωση σώσαμε την ήδη-αλλαγμένη τιμή 0 — οπότε το αρχείο καταγράφει πια το πείραμα και όχι την προεπιλογή. Υπενθύμιση να σώζεις *πριν* επεξεργαστείς, όχι μετά.

### 3.4 Μονιμοποίηση της αλλαγής με `export`

Η παραπάνω απόδοση κρατάει όσο κρατάει η συνεδρία. Το άνοιγμα νέου τερματικού σου δίνει φρέσκο κέλυφος με φρέσκο περιβάλλον, και το `HISTSIZE` επιστρέφει στο 1000 γιατί η τιμή δεν γράφτηκε πουθενά. Για να κάνεις μια μεταβλητή επίμονη πρέπει πρώτα να τη βάλεις στο περιβάλλον με `export`, και μετά να κανονίσεις η απόδοση να συμβαίνει σε κάθε νέο κέλυφος — που γίνεται προσθέτοντας τη γραμμή σε αρχείο εκκίνησης όπως το `~/.bashrc`.

```bash
root@kali:~# HISTSIZE=0
root@kali:~# export HISTSIZE
root@kali:~# bash -c 'echo "child shell sees HISTSIZE=$HISTSIZE"'
child shell sees HISTSIZE=0
root@kali:~# bash -c 'echo "child shell sees HISTFILE=$HISTFILE"'
child shell sees HISTFILE=
root@kali:~# echo 'export HISTSIZE=0' >> ~/.bashrc
```

Οι δύο πρώτες εντολές είναι το τελετουργικό δύο βημάτων: απόδωσε την τιμή, μετά σημάδεψε τη μεταβλητή για εξαγωγή. Η σειρά μετράει — το να εξάγεις όνομα που δεν έχει ακόμα τιμή δεν εξάγει τίποτα — και το `export HISTSIZE=0` σε μία εντολή είναι η συμπαγής μορφή που κάνει και τα δύο μαζί. Η τρίτη εντολή αποδεικνύει το ζήτημα, και είναι η επίδειξη που κάνει τη διάκριση κελύφους-περιβάλλοντος συγκεκριμένη: το `bash -c` ξεκινάει *νέο* κέλυφος, και επειδή το `HISTSIZE` εξήχθη, εκείνη η θυγατρική διεργασία κληρονόμησε την τιμή 0 και την τύπωσε. Η τέταρτη εντολή είναι το πείραμα ελέγχου, ρωτώντας το ίδιο παιδί για το `HISTFILE` που δεν εξήχθη ποτέ — το παιδί αναφέρει κενή τιμή παρότι το γονικό κέλυφος το έχει ορισμένο. Τίποτα σε αυτό δεν είναι σφάλμα· είναι ο κανόνας κληρονομικότητας να κάνει ακριβώς ό,τι λέει.

Η τελευταία γραμμή κάνει την αλλαγή να επιζεί μελλοντικών συνεδριών προσαρτώντας στο `~/.bashrc` — το script που το bash τρέχει κάθε φορά που ξεκινάει διαδραστικό κέλυφος. Ο τελεστής `>>` προσαρτά αντί να αντικαθιστά — η σωστή επιλογή για αρχεία εκκίνησης που ήδη περιέχουν ρυθμίσεις· η χρήση `>` εδώ θα έσβηνε ό,τι υπήρχε, συμπεριλαμβανομένων των γραμμών που ορίζουν το prompt και τα aliases σου. Ποιο αρχείο να επεξεργαστείς εξαρτάται από το κέλυφος και τη στιγμή: το `~/.bashrc` για διαδραστικά κελύφη bash, το `~/.bash_profile` ή `~/.profile` για κελύφη login, το `/etc/environment` ή αρχείο κάτω από το `/etc/profile.d/` για ρυθμίσεις σε όλο το σύστημα που ισχύουν για κάθε χρήστη. Μια αλλαγή στο `~/.bashrc` πιάνει στο *επόμενο* κέλυφος που ξεκινάς, ή αμέσως στο τρέχον αν το φορτώσεις με το χέρι με `source ~/.bashrc` — εντολή που αξίζει να θυμάσαι, αφού γλιτώνει αποσύνδεση και επανασύνδεση για κάθε επεξεργασία.

### 3.5 Δημιουργία και διαγραφή δικών σου μεταβλητών

Οι μεταβλητές δεν χρειάζεται να είναι προ-ορισμένες από το σύστημα· μπορείς να τις φτιάχνεις, να τις ονομάζεις όπως θέλεις και να τις χρησιμοποιείς ως συντομογραφία για τιμές που πληκτρολογείς συχνά. Εδώ φτιάχνεται μεταβλητή για να κρατάει όνομα χώρου.

```bash
root@kali:~# url_variable="example.com"
root@kali:~# echo $url_variable
example.com
root@kali:~# echo "the target is $url_variable"
the target is example.com
root@kali:~# url_variable=example.org
root@kali:~# echo $url_variable
example.org
root@kali:~# unset url_variable
root@kali:~# echo $url_variable

root@kali:~#
```

Η απόδοση δημιουργεί τη μεταβλητή και το `echo $url_variable` τη διαβάζει πίσω· η δεύτερη μορφή δείχνει την αντικατάσταση να δουλεύει μέσα σε μεγαλύτερη συμβολοσειρά — έτσι οι μεταβλητές κερδίζουν το ψωμί τους σε scripts. Η επανα-απόδοση δείχνει ότι μια μεταβλητή μπορεί να αλλάξει οποτεδήποτε απλώς αποδίδοντάς της ξανά, και οι δύο τελευταίες εντολές κάνουν το αντίθετο: το `unset` αφαιρεί τη μεταβλητή εντελώς από το κέλυφος, και το `echo` που ακολουθεί τυπώνει κενή γραμμή — γιατί μια αόριστη μεταβλητή αναπτύσσεται σε τίποτα αντί να παράγει σφάλμα.

Αυτή η σιωπηλή ανάπτυξη είναι παγίδα που αξίζει να ονομαστεί, γιατί scripts που αποτυγχάνουν μυστηριωδώς συνήθως αποτυγχάνουν εδώ: αν μια μεταβλητή είναι αόριστη ή γραμμένη λάθος, το `$name` γίνεται κενή συμβολοσειρά και η εντολή τρέχει με όρισμα που λείπει αντί να παραπονιέται. Δύο άμυνες είναι στάνταρ. Τα εισαγωγικά, που μετατρέπουν μια τιμή που λείπει σε κενό όρισμα αντί για καθόλου όρισμα — το `echo "$url_variable"` είναι ασφαλέστερο από το `echo $url_variable` σε κάθε πλαίσιο όπου η τιμή μπορεί να περιέχει κενά ή να είναι κενή. Και η μορφή `${var:?μήνυμα}`, που κάνει το κέλυφος να ματαιώνεται με το μήνυμά σου αν η μεταβλητή είναι αόριστη — ο σωστός τρόπος να ελέγχεις απαιτούμενη είσοδο σε script: `: "${url_variable:?please set url_variable}"`.

Η άλλη συνήθεια αυτής της υποενότητας είναι τα εισαγωγικά στην απόδοση. Το `url_variable="example.com"` δεν χρειάζεται εισαγωγικά για τιμή χωρίς κενά, αλλά το `url_variable="the example domain"` θα ερμηνευόταν χωρίς αυτά ως απόδοση του `the` και μετά εντολή που λέγεται `example domain` — λάθος που παράγει ένα από τα πιο μπερδεμένα σφάλματα κελύφους που θα συναντήσεις. Το να βάζεις σε εισαγωγικά τη δεξιά μεριά μιας απόδοσης δεν είναι ποτέ λάθος — οπότε αξίζει να το κάνεις από προεπιλογή.

### 3.6 Οι μεταβλητές που αξίζει να ξέρεις

Το περιβάλλον δεν είναι ακαδημαϊκό θέμα· μια χούφτα μεταβλητές αλλάζουν πώς συμπεριφέρεται το σύστημα για σένα, και το να τις ξέρεις μετατρέπει πολλές κατηγορίες μπερδεμένης αποτυχίας σε διάγνωση μίας γραμμής.

Το `PATH` είναι η σημαντικότερη από αυτές, και το συναντήσαμε στο Μέρος 1ο (ενότητα 2.8): μια λίστα καταλόγων χωρισμένων με άνω-κάτω τελεία που το κέλυφος ψάχνει, με σειρά, για την εντολή που πληκτρολόγησες. Το `echo $PATH` δείχνει τη λίστα σου, και το να προσαρτάς σε αυτήν είναι συνηθισμένη λειτουργία — το `export PATH="$PATH:/opt/tools/bin"` κάνει κατάλογο με δικά σου scripts εκτελέσιμο με όνομα. Και αξίζει να καταλάβεις ότι η *σειρά* καθορίζει ποιος κερδίζει όταν δύο κατάλογοι κρατούν πρόγραμμα με ίδιο όνομα. Η οπτική ασφαλείας είναι πραγματική και στις δύο κατευθύνσεις: ένα `PATH` που περιλαμβάνει `.` (τον τρέχοντα κατάλογο) αφήνει ένα κακόβουλο `ls` σε κοινόχρηστο φάκελο να εκτελεστεί από ανυποψίαστο χρήστη, και ένας εγγράψιμος κατάλογος νωρίς στο `PATH` του root είναι κλασική κλιμάκωση προνομίων.

Το `HOME` είναι ο προσωπικός σου κατάλογος και είναι αυτό στο οποίο αναπτύσσεται το `~`· κάθε πρόγραμμα που αποθηκεύει αρχείο ρυθμίσεων το χρησιμοποιεί — οπότε μια λάθος τιμή για χρήστη που τρέχει υπηρεσία είναι συνηθισμένη πηγή προβλημάτων «ο daemon δεν βρίσκει το config του». Τα `USER` και `LOGNAME` ονομάζουν τον τρέχοντα λογαριασμό, και το `SHELL` καταγράφει το κέλυφος login σου. Το `PS1` είναι η συμβολοσειρά κύριου prompt — η μορφή του prompt του κελύφους σου. Γι' αυτό το prompt σε αυτόν τον οδηγό γράφει `root@kali:~#`, και γιατί το να αλλάξεις το `PS1` το αλλάζει ακαριαία — με κωδικούς χρώματος αν θέλεις. Τα `HISTFILE`, `HISTSIZE` και `HISTFILESIZE` κυβερνούν το ιστορικό εντολών, όπως είδαμε. Τα `LANG` και `LC_ALL` ορίζουν τη γλώσσα, την κωδικοποίηση χαρακτήρων και τις συμβάσεις μορφοποίησης που τα προγράμματα χρησιμοποιούν για μηνύματα και ταξινόμηση — και είναι ο λόγος που ένα script συμπεριφέρεται διαφορετικά σε δύο μηχανήματα με πανομοιότυπο λογισμικό: το `sort` ταξινομεί γράμματα διαφορετικά κάτω από διαφορετικά locales, και οι ημερομηνίες τυπώνονται στην τοπική μορφή. Τα `EDITOR` και `VISUAL` αποφασίζουν ποιον editor ανοίγουν για σένα εργαλεία όπως τα `crontab -e`, `git commit` και `visudo` — γι' αυτό το `export EDITOR=nano` είναι από τα πρώτα πράγματα που ένας αρχάριος πρέπει να κάνει. Και το `LD_PRELOAD` αξίζει αναφορά με όνομα, γιατί ζητάει από τον δυναμικό φορτωτή να φορτώσει shared library σε κάθε διεργασία που το κέλυφος ξεκινάει — νόμιμο εργαλείο αποσφαλμάτωσης και συμβατότητας, και ταυτόχρονα γνωστό πρωτόγονο κλιμάκωσης προνομίων όταν μπορεί να οριστεί για SUID εκτελέσιμο. Το να το βλέπεις σε περιβάλλον σε παραγωγικό σύστημα αξίζει διερεύνηση.

Παρμένα μαζί, τα τρία θέματα αυτού του μέρους — δίκτυα, διεργασίες και περιβάλλον — είναι το στρώμα του Linux που κάθεται ανάμεσα στο «μπορώ να χρησιμοποιώ τη γραμμή εντολών» και το «μπορώ να διαχειρίζομαι ή να αξιολογώ αυτό το μηχάνημα». Μια διεπαφή με λάθος διεύθυνση, μια διεργασία που τρώει πυρήνα, ένα όνομα που επιλύεται από λάθος resolver: αυτές είναι οι συνηθισμένες βλάβες, και οι παραπάνω εντολές είναι οι συνηθισμένες απαντήσεις σε αυτές.

## 5. Ασκήσεις εξάσκησης

Οι εντολές αυτού του μέρους γίνονται δικές σου μόνο όταν τις έχεις πληκτρολογήσει ο ίδιος — ορίστε λοιπόν μια σύντομη ακολουθία που χτίζει πάνω στη δουλειά που έκανες στο Μέρος 1ο και γυμνάζει όλα τα παραπάνω. Δούλεψε σε εικονική μηχανή ή container, και πάρε πρώτα snapshot.

1. **Δίκτυα.** Κατέγραψε τη διεύθυνση, τη μάσκα, τη διεύθυνση MAC, την πύλη και τον resolver της διεπαφής σου. Άλλαξε τη διεύθυνση με το χέρι και απόδειξε ότι η αλλαγή είναι προσωρινή επανεκκινώντας την υπηρεσία δικτύωσης. Πλαστογράφησε τη διεύθυνση MAC, μετά τρέξε `dhclient` και εξήγησε ποια τιμή επανήλθε και γιατί. Τέλος, ζήτα από το `dig` τις εγγραφές A, MX και NS ενός χώρου που ελέγχεις, και πες σε μία πρόταση τι σου λέει κάθε τύπος εγγραφής.
2. **Διεργασίες.** Βρες τη διεργασία που χρησιμοποιεί την περισσότερη μνήμη, και αυτήν που χρησιμοποιεί την περισσότερη CPU. Τρέξε μια μακριά δουλειά στη χαμηλότερη προτεραιότητα στο παρασκήνιο, δείξε την με `jobs -l`, μετά σταμάτησέ την, στείλε την πάλι πίσω και φέρτην μπροστά. Προγραμμάτισε μια ακίνδυνη εντολή με `at` να τρέξει σε δύο λεπτά από τώρα και επιβεβαίωσε ότι έτρεξε. Στείλε `SIGTERM` σε διεργασία της επιλογής σου, και μόνο αν αυτό αποτύχει κλιμάκωσε σε `SIGKILL` — εξηγώντας γραπτά γιατί η σειρά μετράει.
3. **Περιβάλλον.** Τύπωσε την τιμή του `HISTSIZE`, σώσε την σε αρχείο στον προσωπικό σου κατάλογο, άλλαξέ την μόνο για το τρέχον κέλυφος, και απόδειξε ότι ένα θυγατρικό κέλυφος δεν βλέπει την αλλαγή. Μετά εξήγαγέ την, απόδειξε ότι ένα θυγατρικό κέλυφος τη βλέπει, και τέλος κάντην μόνιμη στο `~/.bashrc`. Φτιάξε δική σου μεταβλητή, χρησιμοποίησέ την σε εντολή, και διέγραψέ την με `unset` — σημειώνοντας σε τι αναπτύσσεται μια αόριστη μεταβλητή.

Αν μπορείς να ολοκληρώσεις αυτές τις τρεις ασκήσεις χωρίς να αναζητήσεις τίποτα, νιώθεις άνετα με το στρώμα του Linux που κάθεται ανάμεσα στη χρήση της γραμμής εντολών και τη διαχείριση συστήματος — και είσαι έτοιμος για το Μέρος 3ο.

## Κλείσιμο

Τα τρία θέματα αυτού του μέρους μοιράζονται ένα θέμα που χάνεται εύκολα όσο απομνημονεύεις παραμέτρους: όλα αφορούν **κατάσταση από την οποία κάτι άλλο εξαρτάται**. Μια διεύθυνση εξαρτάται από κάθε σύνδεση που το μηχάνημα κάνει· μια διεργασία εξαρτάται από όποιον χρησιμοποιεί την υπηρεσία που παρέχει· μια μεταβλητή περιβάλλοντος εξαρτάται από τις θυγατρικές διεργασίες που την κληρονομούν και δεν αναφέρουν ποτέ τι τους δόθηκε. Γι' αυτό οι εντολές εδώ είναι πιο βαριές σε συνέπειες από αυτές του Μέρους 1ου — ένα λάθος δεν παράγει μήνυμα σφάλματος, παράγει μηχάνημα που συμπεριφέρεται διαφορετικά από ό,τι περίμενες, συχνά για κάποιον άλλον.

Δύο συνήθειες από το Μέρος 1ο αξίζει να μεταφερθούν, γιατί καλύπτουν το μεγαλύτερο μέρος του ρίσκου. Η πρώτη είναι να *κοιτάς πριν αλλάξεις οτιδήποτε*: διάβαζε αρχείο ρυθμίσεων πριν το αντικαταστήσεις, τρέχε `pgrep` πριν τρέξεις `pkill`, τύπωνε πίνακα διευθύνσεων πριν αλλάξεις διεπαφή, και σώζε τιμή πριν την καταργήσεις ή την ξαναποδώσεις. Η δεύτερη είναι να *έχεις δρόμο επιστροφής*: ένα snapshot, μια δεύτερη κονσόλα, ή επαναφορά προγραμματισμένη με `at` πριν αγγίξεις το δίκτυο.

Το **Μέρος 3ο** είναι η συνέχεια και ξεκινάει ακριβώς εκεί που σταματάει αυτός ο οδηγός. Το [Linux για Αρχάριους (Μέρος 3ο): Scripting, Προγραμματισμός Εργασιών και Υπηρεσίες](03-linux-for-beginners-part-03.md) καλύπτει το shell **scripting και αυτοματισμό** — συνθήκες, βρόχους, συναρτήσεις και τις μεταβλητές που μόλις γνώρισες, συναρμολογημένα σε προγράμματα που κάνουν μια μέρας δουλειά σε ένα δευτερόλεπτο — μαζί με **προγραμματισμό** με `cron` και **διαχείριση υπηρεσιών** με `service`/`systemctl`, συμπεριλαμβανομένων των Apache web server, OpenSSH και FTP. Πέρα από τα τρία μέρη, φυσικά επόμενα βήματα είναι να γράφεις δικά σου systemd units και timers, **διαχείριση πακέτων και ρυθμίσεων** σε περισσότερα από ένα μηχανήματα, και βαθύτερη μελέτη του **μοντέλου δικαιωμάτων και προνομίων**. Το καθένα χτίζει κατευθείαν πάνω στην παραπάνω ύλη, και το καθένα είναι πολύ λιγότερο εκφοβιστικό αφού η μετακίνηση στο σύστημα αρχείων, η ανάγνωση μακροσκελούς λίστας και η επιθεώρηση τρέχουσας διεργασίας νιώθουν όλα δεύτερη φύση.
